# Agent Loop Architecture, Multi-Agent Design, Verification, Reliability, Security, Latency and Evaluation for LLM Agent Harnesses (notes for Xylo)

Scope note: These notes cover harness-level techniques that work with third-party models and need no fine-tuning. Context compaction, long-term memory and tool-description design are left to other researchers and appear only where unavoidable. All arXiv IDs below were checked against the arXiv API on 2026-10-31 (titles, authors and dates match). Quantitative claims come from paper abstracts or primary pages unless marked otherwise. "Harness note" items under each section's Inferences are my implementation suggestions for Xylo, not claims from the sources. **[LOCAL]** marks findings that matter especially for small local models.

---

## 1. Agent loop and planning: ReAct, plan-and-execute, ReWOO, Plan-and-Solve, todo lists / plan recitation, LATS, Reflexion, Self-Refine. Which still matter with 2025–2026 frontier reasoning models, and which help weaker local models?

### Takeaway
With frontier reasoning models, a minimal ReAct-style loop (one tool, linear history) is already near the state of the art on SWE-style tasks. Prompt-level "thought" scaffolds such as the think tool and ReAct thoughts are now largely subsumed by native or interleaved reasoning. What still pays off for strong models is persistent, external plan state: a todo or feature list that is recited and updated, progress files, and one-feature-at-a-time discipline. These matter on long-horizon runs. For small local models, planner/executor separation (ReWOO, Plan-and-Act), execution-guided plan repair (EvoFlux) and verification with external feedback give large relative gains. Intrinsic self-reflection without external signals does not reliably help any model.

### Cited Findings

**Classic loop and planning papers (2022–2024; headline numbers mostly superseded by stronger base models)**
- **ReAct: Synergizing Reasoning and Acting in Language Models.** Yao et al. (Princeton / Google), 2022, ICLR 2023, [arXiv:2210.03629](https://arxiv.org/abs/2210.03629). The model interleaves "thought" text with tool actions and observations. On ALFWorld and WebShop it beat imitation-learning and RL methods by 34% and 10% absolute success, using only 1–2 in-context examples. On HotpotQA and FEVER, grounding in a Wikipedia API reduced hallucination compared with chain-of-thought (CoT). — [arXiv abstract](https://arxiv.org/abs/2210.03629)
- **Plan-and-Solve Prompting.** Wang et al., ACL 2023, [arXiv:2305.04091](https://arxiv.org/abs/2305.04091). Zero-shot prompt: "devise a plan dividing the task into subtasks, then carry out the subtasks". PS+ adds detailed instructions to reduce calculation and missing-step errors. With GPT-3 it beat Zero-shot-CoT on all 10 datasets and was comparable to 8-shot CoT on math. — [arXiv](https://arxiv.org/abs/2305.04091)
- **ReWOO: Decoupling Reasoning from Observations.** Xu et al., 2023, [arXiv:2305.18323](https://arxiv.org/abs/2305.18323). A Planner writes the whole tool-call plan up front with variable placeholders (#E1, #E2...). Workers execute the plan, and a Solver composes the answer. This avoids re-sending the growing prompt on every step. Results: 5x token efficiency and +4% accuracy on HotpotQA, more robust to tool failures. Planner reasoning was offloaded from 175B GPT-3.5 to a 7B LLaMA, though that step used instruction fine-tuning. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2305.18323)
- **LLMCompiler: An LLM Compiler for Parallel Function Calling.** Kim et al. (UC Berkeley), ICML 2024, [arXiv:2312.04511](https://arxiv.org/abs/2312.04511). A planner emits a DAG of function calls, and a task-fetching unit dispatches independent calls in parallel. Versus ReAct: up to 3.7x lower latency, up to 6.7x cost savings, up to ~9% accuracy gain. Works with open and closed models. — [arXiv](https://arxiv.org/abs/2312.04511)
- **Plan-and-Act: Improving Planning of Agents for Long-Horizon Tasks.** Erdogan et al., ICML 2025, [arXiv:2503.09572](https://arxiv.org/abs/2503.09572). A Planner generates structured high-level plans and an Executor turns them into environment actions. Results: 57.58% on WebArena-Lite (SOTA at the time) and 81.36% text-only on WebVoyager. Note: the planner was trained on synthetic plan data, so this is not purely a prompting technique. — [arXiv](https://arxiv.org/abs/2503.09572)
- **LATS: Language Agent Tree Search.** Zhou et al., 2023 (ICML 2024), [arXiv:2310.04406](https://arxiv.org/abs/2310.04406). Monte Carlo Tree Search over actions, with an LM-based value function, self-reflection and environment feedback. Results: 92.7% pass@1 on HumanEval with GPT-4, and an average score of 75.9 on WebShop with GPT-3.5, comparable to fine-tuning. Tree search requires environment states that can be reset or forked. — [arXiv](https://arxiv.org/abs/2310.04406)
- **Reflexion: Language Agents with Verbal Reinforcement Learning.** Shinn et al., NeurIPS 2023, [arXiv:2303.11366](https://arxiv.org/abs/2303.11366). After a failed trial, the agent writes a verbal reflection on the task feedback into episodic memory and retries. Result: 91% pass@1 on HumanEval versus 80% for GPT-4. The feedback can be scalar or free-form, external or self-simulated (e.g., self-generated unit tests). — [arXiv](https://arxiv.org/abs/2303.11366)
- **Self-Refine: Iterative Refinement with Self-Feedback.** Madaan et al., NeurIPS 2023, [arXiv:2303.17651](https://arxiv.org/abs/2303.17651). A single model generates, critiques and refines its own output. About +20% absolute on average across 7 tasks with GPT-3.5/4. — [arXiv](https://arxiv.org/abs/2303.17651)
- **Counter-evidence: Large Language Models Cannot Self-Correct Reasoning Yet.** Huang, Chen, Mishra et al. (UIUC / Google DeepMind), ICLR 2024, [arXiv:2310.01798](https://arxiv.org/abs/2310.01798). Without external feedback, LLMs struggle to self-correct reasoning, and performance sometimes degrades after self-correction. Self-Refine/Reflexion-style gains depend on external signals: tests, environment state, tools. — [arXiv](https://arxiv.org/abs/2310.01798)

**Plan recitation, todo lists and persistent plan state (2025)**
- **Manus, "Context Engineering for AI Agents: Lessons from Building Manus".** Yichao "Peak" Ji, July 18, 2025. Manus creates and continuously rewrites a `todo.md` on complex tasks, which average about 50 tool calls. Reciting the plan pushes the global goal into the most recent context, countering "lost-in-the-middle" drift. Other lessons: keep failed actions and stack traces in context so the model updates its beliefs ("keep the wrong stuff in"). Add controlled variation in serialization so the agent doesn't fall into a repetitive few-shot rut; in a 20-resume batch review it fell into a repetitive rhythm. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- **Anthropic, "Effective harnesses for long-running agents".** Justin Young, Nov 26, 2025. A frontier model looping with compaction still failed in two ways. It one-shotted too much and ran out of context mid-feature, and later sessions declared victory early. The fix uses two prompts on the same harness. An **initializer agent** writes `init.sh`, `claude-progress.txt`, an initial git commit, and a JSON feature list (200+ features for a claude.ai clone, all initially failing, with a `passes` field). A **coding agent** works on one feature at a time, commits, updates the progress file, and may only flip `passes`. JSON was chosen because models are less likely to overwrite it inappropriately than Markdown. Each session starts with a fixed routine: pwd, read progress, git log, feature list, run `init.sh`, run a basic end-to-end test. Prompting for browser-automation end-to-end testing (Puppeteer MCP) "substantially improved" results over unit tests or curl checks. No benchmark numbers were reported. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **Anthropic "think" tool (Mar 2025, updated Dec 15, 2025).** The think tool is a no-op tool with a `thought` parameter that lets the model pause mid-trajectory. On τ-bench airline with Claude 3.7 Sonnet, pass^1 was 0.584 for think + optimized prompt versus 0.332 baseline and 0.412 for extended thinking. pass^5 was 0.340 versus 0.100. On SWE-bench the isolated effect was about +1.6%. The page is internally inconsistent: its prose quotes 0.570 vs 0.370. **Superseded:** the Dec 15, 2025 update recommends extended thinking "instead of a dedicated think tool in most cases." — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-think-tool)
- **Anthropic multi-agent research system:** extended thinking serves as a planning scratchpad for the lead agent, and subagents "reassess after each tool result" (interleaved thinking). — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)

**What still matters with frontier models (2025–2026 evidence)**
- **mini-SWE-agent** (SWE-agent team): about 100 lines of Python, bash as the only tool, a completely linear message history, and each action run via an independent `subprocess.run`. Reported at >74% on SWE-bench Verified with frontier models; one listing cites Gemini 3 Pro at 74%. Scores depend on the model. — [GitHub](https://github.com/SWE-agent/mini-swe-agent)
- **Live-SWE-agent.** Xia et al. (UIUC), Nov 2025, [arXiv:2511.13646](https://arxiv.org/abs/2511.13646). Starts from mini-SWE-agent (bash only) and lets the agent create and modify its own tools and scaffold at runtime while solving a task. Results: 77.4% on SWE-bench Verified without test-time scaling and 45.8% on SWE-bench Pro, both the best reported at the time. — [arXiv](https://arxiv.org/abs/2511.13646)
- **Beyond the Model: Demystifying Harness Effects in SE Agents.** Hu et al., Sep 2026, [arXiv:2609.32459](https://arxiv.org/abs/2609.32459). Evaluated mini-SWE-agent vs OpenCode with 10 Qwen/DeepSeek open-weight models on SWE-bench Pro, ProgramBench and GitTaskBench. **Complex harnesses give diminishing gains on SWE-style issue repair as model capability rises**, but can help stronger models on open-ended repository-level tasks. Component ablation on ProgramBench: structured tool use and task-specific subagents gave the most stable gains, while context compression and general-purpose subagents can hurt repository generation. Explicit planning was among the ablated components. Combined, the NanoHarness gave +7.37pp (Qwen3.7-Max) and +6.21pp (DeepSeek-V4-Pro) over mini-SWE-agent. — [arXiv](https://arxiv.org/abs/2609.32459)
- **Scaffold Effects on GAIA: A Controlled Comparison.** Starace, Jun 2026, [arXiv:2606.08529](https://arxiv.org/abs/2606.08529). A pre-registered comparison of ReAct vs Planner-Actor-Rater (multi-agent) vs planner-then-executor, across Claude Opus 4.7, Sonnet 4.6, Haiku 4.5, Gemini 3.1 Pro Preview and GPT-5.5. Scaffold choice alone moved accuracy by up to **28pp within one model** (Opus, Level 2). The prediction that stronger models are less scaffold-sensitive was **rejected**: the most capable Anthropic model gained the most from structured scaffolds at Level 2. Structured scaffolds made fewer tool calls and recovered more often from mid-trajectory errors at the harder level. Gemini with planner-then-executor was the cheapest cell at both levels and the most accurate at Level 2. — [arXiv](https://arxiv.org/abs/2606.08529)
- **HAL (Holistic Agent Leaderboard).** Kapoor et al. (Princeton), Oct 2025, [arXiv:2510.11977](https://arxiv.org/abs/2510.11977). Across 21,730 rollouts (9 models × 9 benchmarks, about $40k), **higher reasoning effort reduced accuracy in the majority of runs**. — [arXiv](https://arxiv.org/abs/2510.11977)

**Small/local model planning evidence**
- **EvoFlux.** Bhandari et al., Jun 2026, [arXiv:2606.12674](https://arxiv.org/abs/2606.12674). Small models (1.5–4B) produce plausible plans that fail at execution: unavailable tools, missing arguments, broken dependencies. EvoFlux represents the plan as a graph of tool calls, executes it against live MCP servers, and uses the errors to guide edits: replace a tool, fix parameters, insert or remove steps. On MCP-Bench (28 live servers, 250 tools), execution success rose from about 3% to 17–24% across four small planners. SFT/DPO on the same data matched or underperformed zero-shot. ReAct reached higher peaks on stronger planners but cost 4–20x more planner tokens per solved task. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2606.12674)
- **Scaling Small Agents Through Strategy Auctions (SALE).** Alazraki et al., Feb 2026, [arXiv:2602.02751](https://arxiv.org/abs/2602.02751). Small agents' performance "fails to scale with task complexity" on deep search and coding. Agents of different sizes bid with short strategic plans, which are scored on cost and value. This cut reliance on the largest agent by 52% and overall cost by 35%, and improved on the largest agent's pass@1. Description-based routers underperformed or failed to save cost. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2602.02751)
- **Small LLMs Are Weak Tool Learners: A Multi-LLM Agent (α-UMi).** Shen et al., 2024, [arXiv:2401.07324](https://arxiv.org/abs/2401.07324). Splitting tool use into planner, caller and summarizer roles beats a single small LLM. This requires fine-tuning each role, so it is out of scope as-is, but the role decomposition is reusable with prompting. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2401.07324)
- **Small Language Models for Agentic Systems (survey).** Sharma & Mehta, Oct 2025, [arXiv:2510.03847](https://arxiv.org/abs/2510.03847). Claims that guided decoding (XGrammar, Outlines), strict JSON-Schema outputs and validator-first tool execution "close much of the capability gap", letting SLMs match LLMs on function calling at 10–100x lower token cost. Recommends an SLM-default, LLM-fallback design with verifier cascades, and notes the limits on open-domain reasoning and some long-horizon planning. This is a survey or position piece, not a controlled study. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2510.03847)
- **Scaling LLM Test-Time Compute Optimally.** Snell et al. (Google DeepMind / UC Berkeley), Aug 2024, [arXiv:2408.03314](https://arxiv.org/abs/2408.03314). Compute-optimal, difficulty-adaptive allocation of test-time compute is more than 4x as efficient as best-of-N. On problems where a smaller model has non-trivial success, test-time compute can beat a 14x larger model in FLOPs-matched evaluation. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2408.03314)

### Inferences
- **Harness note (default loop):** Keep the core loop ReAct-shaped and linear: model → tool calls → observations appended. mini-SWE-agent and Live-SWE-agent show this suffices for frontier models. Do not add heavyweight planning layers by default for cloud reasoning models. Make planning, verification and subagent features opt-in modules, so they can be ablated per model, following the NanoHarness approach.
- **Harness note (todo/plan tool):** Ship a first-class `todo_write`/`update_plan` tool backed by structured state (JSON with status per item), not free Markdown. Re-inject the current plan into the most recent context on each turn or every N turns. This is recitation à la Manus. Persist it to disk so a resumed or forked run can read it. For long tasks, adopt Anthropic's pattern: a feature/acceptance list where the agent may only flip a pass flag, a progress log file, a git checkpoint per unit of work, and a fixed "startup routine" prompt for every new session or fork.
- **Harness note (plan-then-execute mode for local models) [LOCAL]:** Offer a "ReWOO/LLMCompiler mode". The model emits a full tool-call DAG once, the harness executes independent nodes in parallel, and on execution errors it feeds structured errors back for targeted plan repair (EvoFlux-style) rather than re-running a free ReAct loop. For a 3–8B local model this reduces the number of long-context model calls. That matters on consumer GPUs, where prefill dominates latency. It also gives the harness a deterministic structure to validate with JSON-Schema-constrained decoding.
- **Harness note (reasoning effort):** Don't assume max reasoning effort is best: HAL found it reduced accuracy in most runs. Expose effort per subagent and per phase, e.g., high for planning and verification, low for mechanical edits.
- **Reflection:** Implement Reflexion-style retries only when there is an external signal: test failure, tool error, linter output, validator failure. Plain "reflect on your answer" loops without new information are unsupported by evidence (Huang et al.).
- **Tree search (LATS):** Practical only where the environment can be cheaply snapshotted, e.g., git worktrees, container checkpoints or VM snapshots. For a desktop harness, a "parallel attempts in isolated worktrees + selection" pattern (Section 3) is the realistic form of search.
- The GAIA scaffold study and HAL suggest the "frontier models don't need scaffolds" heuristic is task-dependent. On harder, multi-step research tasks, structured scaffolds still moved strong models by double digits.

### Gaps
- I found no controlled 2025–2026 study isolating todo-list recitation as a variable with frontier models. Evidence is practitioner reports (Manus, Anthropic) and component ablations whose per-component planning numbers I could not read in full (2609.32459).
- I did not find a head-to-head of ReWOO/LLMCompiler-style planning versus ReAct on 2026 frontier models. The original speedups were measured against GPT-3.5/4-era ReAct.
- LATS/MCTS cost numbers for modern models were not found.

## 2. Multi-agent and subagents: orchestrator-worker, context isolation, condensed returns, when subagents help vs hurt, cost multipliers, failure taxonomies

### Takeaway
Multi-agent (orchestrator-worker) setups help mainly on breadth-first, parallelizable tasks like research and search. Anthropic measured +90.2% over a single agent at about 15x the tokens of chat. They hurt on tightly coupled, sequential work such as most coding, where dispersed decisions conflict. The best-supported pattern for a coding/desktop harness is a single-threaded main agent with **narrow, contract-bound subagents**. Each gets a fresh context, a clear input/output contract, and returns condensed results; examples are search/investigation, review/verification, or a skill packaged as a subagent. Centralized verification is better than independent agents.

### Cited Findings
- **Anthropic, "How we built our multi-agent research system".** Hadfield, Zhang, Lien, Scholz, Fox, Ford, Jun 13, 2025.
  - A Claude Opus 4 lead with Sonnet 4 subagents outperformed single-agent Opus 4 by **90.2%** on an internal research eval.
  - On BrowseComp, three factors explained 95% of performance variance, and **token usage alone explained 80%**; the other two were tool-call count and model choice. Upgrading to Sonnet 4 beat doubling the token budget on Sonnet 3.7.
  - Agents use about **4x** the tokens of chat; multi-agent systems about **15x**.
  - The lead spawns 3–5 subagents in parallel, and each uses 3+ tools in parallel. This cut research time by up to **90%** for complex queries.
  - Effort scaling is embedded in the prompt:
    - simple fact-finding: 1 agent, 3–10 tool calls
    - comparisons: 2–4 subagents, 10–15 calls each
    - complex research: 10+ subagents
    - Early versions spawned 50 subagents for simple queries.
  - Each delegation needs an objective, an output format, tool and source guidance, and task boundaries; vague delegation caused duplicated work.
  - Subagents act as "intelligent filters" and return condensed findings. Large outputs can be written to the filesystem and passed back as lightweight references to avoid a "game of telephone".
  - **Not a good fit:** most coding tasks (few parallelizable parts), tasks needing shared context or many inter-agent dependencies, and low-value tasks.
  - The synchronous lead (waiting for each subagent batch) blocks steering. Asynchronous execution adds coordination, state-consistency and error-propagation problems.
  - [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Cognition, "Don't Build Multi-Agents".** Walden Yan, Jun 12, 2025. Two principles: (1) share context, meaning full agent traces, not just messages; (2) "actions carry implicit decisions, and conflicting decisions carry bad results". In the Flappy Bird example, parallel subagents built a Mario-style background and a mismatched bird. Recommended: a single-threaded linear agent, plus a context-compression model for very long tasks. Claude Code-style subagents that only answer a well-defined question (not write code) were cited as acceptable, because they keep investigative work out of the main history. — [Cognition blog](https://cognition.com/blog/dont-build-multi-agents)
- **Why Do Multi-Agent LLM Systems Fail? (MAST).** Cemri, Pan, Yang et al. (UC Berkeley), Mar 2025, v3, [arXiv:2503.13657](https://arxiv.org/abs/2503.13657).
  - The paper notes that MAS gains on popular benchmarks "are often minimal".
  - MAST-Data: 1,600+ annotated traces across 7 MAS frameworks.
  - The taxonomy was built from 150 traces with inter-annotator kappa = 0.88. It has 14 failure modes in 3 categories: (i) system design issues, (ii) inter-agent misalignment, (iii) task verification.
  - An LLM-as-judge annotator with high human agreement is released.
  - Failure modes as I recall them from the paper's taxonomy figure (not in the abstract, verify before quoting):
    - disobey task/role specification
    - step repetition
    - loss of conversation history
    - unaware of termination conditions
    - conversation reset
    - fail to ask for clarification
    - task derailment
    - information withholding
    - ignored other agent's input
    - reasoning–action mismatch
    - premature termination
    - no/incomplete verification
    - incorrect verification
  - [arXiv](https://arxiv.org/abs/2503.13657)
- **Towards a Science of Scaling Agent Systems.** Kim, Gu, Park et al., Dec 2025, [arXiv:2512.08296](https://arxiv.org/abs/2512.08296).
  - Setup: 260 controlled configurations, 6 benchmarks, single-agent plus 4 multi-agent architectures (Independent, Centralized, Decentralized, Hybrid), 3 LLM families, with tools, prompts and compute standardized.
  - The change relative to a single agent ranges from **+80.8%** on decomposable financial reasoning to **−70.0%** on sequential planning.
  - Coordination gives diminishing returns once the single-agent baseline is strong (capability saturation).
  - Tool-heavy tasks incur multi-agent overhead.
  - Architectures without centralized verification propagate errors more.
  - A predictive model picks the best architecture for 87% of held-out configurations.
  - [arXiv](https://arxiv.org/abs/2512.08296)
- **Subagents vs Agent Skills.** Piriyakulkij, Lawrence, Curth et al., Sep 2026, [arXiv:2609.09233](https://arxiv.org/abs/2609.09233). Loading skill instructions into the main context becomes brittle as horizons grow, because reasoning degrades as context accumulates. Running a skill package **as a subagent** with a fresh context window outperforms in-context skill execution **when the skill exposes a clear input/output contract** and its instructions encode the procedure. The cost is extra coordination tokens. — [arXiv](https://arxiv.org/abs/2609.09233)
- **When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail.** Li, Jan 2026, [arXiv:2601.04748](https://arxiv.org/abs/2601.04748). Compiling a MAS into a single agent with a skill library "can substantially reduce token usage and latency while maintaining competitive accuracy" (preliminary). Skill-selection accuracy shows a **phase transition**: stable up to a critical library size, then a sharp drop driven by semantic confusability among similar skills. — [arXiv](https://arxiv.org/abs/2601.04748)
- **Harness effects in SE agents.** [arXiv:2609.32459](https://arxiv.org/abs/2609.32459): **task-specific subagents** gave stable improvements, while **general subagents** could hurt repository-generation performance. — [arXiv](https://arxiv.org/abs/2609.32459)
- **Stop Comparing LLM Agents Without Disclosing the Harness.** Zhang et al., May 2026, [arXiv:2605.23950](https://arxiv.org/abs/2605.23950). On SWE-bench Pro, adding a WarpGrep **search subagent** moved each model by 2.1–2.2 points and flipped the ranking of MiniMax 2.5 vs Claude Opus 4.6. — [arXiv HTML](https://arxiv.org/html/2605.23950v1)
- **When and Why Does Multi-Agent Debate Fail?** Chen et al., Oct 2025, [arXiv:2510.20963](https://arxiv.org/abs/2510.20963). Evidence is growing that multi-agent debate (MAD) may not beat, or may significantly underperform, single-agent methods. Competitive debate degenerates into "cheap talk", and consensus-seeking debate filters out informative disagreement (premature consensus). A collaborative non-zero-sum protocol (ColMAD) gains up to 10pp over prior MAD protocols. — [arXiv](https://arxiv.org/abs/2510.20963)
- **LLM Multi-Agent Systems Are Vulnerable to Herding and Runaway Cascades.** Hashemi et al., Oct 2026, [arXiv:2610.30769](https://arxiv.org/abs/2610.30769). LLM populations exposed to each other's choices herd far more than humans and self-correct less. This is relevant to multi-judge or voting designs that share intermediate opinions. — [arXiv](https://arxiv.org/abs/2610.30769)
- **Anthropic long-running harness** (Nov 2025): it remains an open question whether a single general coding agent beats a multi-agent setup with specialized testing, QA or cleanup agents. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- **Harness note (subagent contract):** Every named subagent or supervised fork in Xylo should declare:
  - an objective
  - an input schema
  - an output schema or format (ideally a condensed summary plus artifact paths)
  - a tool allowlist
  - a token and step budget
  - a stop condition

  This mirrors Anthropic's delegation checklist and the "clear I/O contract" condition in 2609.09233. Have subagents write bulky artifacts to files and return references, not full dumps.
- **Harness note (when to fan out):** Default to no fan-out for coding and editing. Allow parallel fan-out for read-only breadth tasks: codebase search, web research, multi-file review, test triage. Make write-capable parallel forks operate in isolated worktrees and merge through the main agent. Cognition's "conflicting implicit decisions" problem argues against parallel writers sharing a target.
- **Harness note (centralized verification):** Put a verification step at the orchestrator, not in each worker. Scaling-laws work shows that architectures without centralized verification propagate errors. MAST's largest actionable bucket is verification and termination.
- **Harness note (effort scaling):** Encode Anthropic-style complexity tiers in the orchestrator prompt and enforce hard caps in code, e.g., max concurrent subagents and max total subagent tokens per user turn. Over-spawning is a documented failure.
- **Harness note (steering + subagents):** Anthropic flags synchronous waiting as blocking steering. Xylo's mid-run steering messages should be routable to running subagents, or should at least be able to cancel or redirect them. That requires async subagent execution with a message channel and cancellation tokens.
- **Cost model:** Budget for about 4x (single agent) and about 15x (multi-agent) chat-equivalent tokens. Show the user a per-run token or cost meter, with an estimate when spawning subagents.
- **Local models [LOCAL]:** Fresh-context subagents are especially valuable for small local models with short effective context. Keep the main loop short and push file-reading and search into throwaway subagent contexts that return summaries. The capability-saturation finding suggests the gain shrinks as the model gets stronger.
- **Skills vs subagents:** Packaging plugins or skills with input/output contracts lets the harness choose at runtime between in-context loading (short tasks) and subagent execution (long tasks). Keep the skill library small or hierarchical to avoid the selection phase transition.

### Gaps
- MAST category percentages and per-mode frequencies were not in the abstract, and I did not verify them from the full text.
- The specific error-amplification factors in 2512.08296 (independent vs centralized) were not in the abstract and are not reported here.
- No published measurement was found of Claude Code / Codex subagent effects on SWE-bench-style scores, apart from the WarpGrep search-subagent example in 2605.23950.

## 3. Self-verification, test-time compute, and how much harness/scaffold choice changes results

### Takeaway
Verification grounded in executable feedback is the most reliable test-time lever: running tests, linting on edit, reproduction scripts, and best-of-N with test-based selection. Intrinsic self-critique and unverified majority voting plateau. Even strong terminal agents catch only about 61% of their own wrong solutions and repair only about half of those. Harness choice for the same model routinely moves scores by 7–16pp, up to 28–48pp in some reports, and token cost by up to 40x. Harness design is a first-class variable, not a detail.

### Cited Findings

**Verification and test-time scaling**
- **Agentless.** Xia, Deng, Dunn, Zhang (UIUC), Jul 2024, [arXiv:2407.01489](https://arxiv.org/abs/2407.01489). A fixed three-phase pipeline replaces an agent loop: localization → repair (sample multiple patches) → patch validation. Validation uses generated reproduction tests plus existing regression tests to select a patch. Result: 32.00% on SWE-bench Lite at $0.70 per issue, the best open-source result at the time. The authors also flagged SWE-bench Lite issues with leaked or insufficient specs. — [arXiv](https://arxiv.org/abs/2407.01489)
- **Large Language Monkeys.** Brown, Juravsky, Ehrlich et al. (Stanford), Jul 2024, [arXiv:2407.21787](https://arxiv.org/abs/2407.21787). Coverage scales log-linearly with sample count. On SWE-bench Lite with DeepSeek-Coder-V2, **15.9% (1 sample) → 56% (250 samples)**. Without automatic verifiers, majority voting and reward models **plateau beyond several hundred samples**. — [arXiv](https://arxiv.org/abs/2407.21787)
- **CodeMonkeys.** Ehrlich et al. (Stanford), Jan 2025, [arXiv:2501.14723](https://arxiv.org/abs/2501.14723). Serial scaling means more iterations per trajectory, with the model writing and running a test script alongside its edit. Parallel scaling means more trajectories per issue. Selection combines voting with model-generated tests and a dedicated selection trajectory. Results: 57.4% on SWE-bench Verified for about $2,300 total. Selecting over an ensemble of top leaderboard submissions reached 66.2%, beating the best member. — [arXiv](https://arxiv.org/abs/2501.14723)
- **Self-Consistency.** Wang et al. (Google), ICLR 2023, [arXiv:2203.11171](https://arxiv.org/abs/2203.11171). Sample diverse reasoning paths and take the majority answer. Gains: GSM8K +17.9%, SVAMP +11.0%, AQuA +12.2%. Applies to tasks with a final answer that can be compared, not to open-ended trajectories. — [arXiv](https://arxiv.org/abs/2203.11171)
- **Can Terminal Agents Trust Their Own Verification?** Luo et al., Sep 2026, [arXiv:2609.38812](https://arxiv.org/abs/2609.38812). Across 10 terminal agents on TerminalBench 2.1, verification is "nearly universal" once a complete candidate exists. But only **61.43% of incorrect candidates are detected** and only **49.36% of detected errors are successfully repaired**. The weakness is detection and repair, not starting verification. (Their fix, SCVD, is distillation, so out of scope, but it gave +9.7 to +16.9pp pass@1 on Qwen3.5 backbones.) — [arXiv](https://arxiv.org/abs/2609.38812)
- **SWE-agent ACI ablations.** Yang, Jimenez, Wettig et al. (Princeton), NeurIPS 2024, [arXiv:2405.15793](https://arxiv.org/abs/2405.15793). SWE-bench Lite with GPT-4 Turbo, 18.0% default:

AgentErrorTaxonomy covers memory, reflection, planning, action and system errors. AgentErrorBench annotates failure trajectories from ALFWorld, GAIA and WebShop. AgentDebug isolates the **root-cause step** and gives targeted corrective feedback. Results: +24% all-correct accuracy and +17% step accuracy over the strongest baseline, and up to **26% relative task-success improvement** when agents retry with that feedback. — [arXiv](https://arxiv.org/abs/2509.25370)
- **AgentRewardBench.** Lù et al. - **Agent-as-a-Judge.** Zhuge et al. (Meta / KAUST), Oct 2024, [arXiv:2410.10934](https://arxiv.org/abs/2410.10934). ### Inferences
- **Harness note (verification gates):** Build verification into the tool layer, not just the prompt:
  1. **Lint/compile/format on edit**, rejecting broken edits with an error message. This is the SWE-agent linter guardrail, about +3pp and fewer cascades.
  2. A `run_tests` / `verify` tool, plus a stop hook that asks "did you run the tests?" before allowing a "done" turn on coding tasks.
  3. For UI or web work, end-to-end checks such as browser automation or screenshots.
  4. Optionally a separate verifier subagent with fresh context that is given the diff and the acceptance criteria, not the worker's reasoning.

  Given the 61% detection and 49% repair rates, the verifier should be independent and should check against objective artifacts.
- **Harness note (best-of-N) [LOCAL]:** Offer an opt-in "N parallel attempts in isolated git worktrees + test-based selection" mode (CodeMonkeys/Agentless pattern). For local models this trades cheap local compute for accuracy, which is the Snell et al. regime where a small model plus test-time compute can beat a larger one. Selection must use executable signals (tests, reproduction scripts). Majority voting or LLM reward without verification plateaus.
- **Harness note (observation windowing):** The SWE-agent ablation (last 5 observations beat full history; a 100-line viewer beat the full file) supports bounded tool outputs: paginated file views and summarized search results. This touches context management, which other researchers cover, but it is an ACI choice.
- **Harness note (root-cause feedback):** When a run fails, have a cheap "debugger" pass locate the first erroneous step and inject targeted corrective feedback, rather than generic "try again" (AgentDebug: up to 26% relative gain).
- **Harness note (self-description):** Publish a Harness Card for Xylo (tools, loop, stop rules, verification, permissions, cache policy) and keep it versioned. It doubles as an internal eval artifact, because the same model under different Xylo configs can differ by 5–15pp.
- **Harness note (stop conditions):** The OpenHands-SDK "VERIFY/MAX_TURNS" and OpenCode "idle-loop" fingerprints show that stop and verify policy is a major harness-specific failure source. Treat it as a tunable, tested component.

### Gaps
- No public, controlled measurement of how much a verifier subagent with fresh context improves over in-loop self-verification on SWE-bench Verified or Terminal-Bench with 2026 frontier models was found.
- Some deltas cited in 2605.23950 (Vercel, Grok 4 xAI scaffold) are secondary citations within that paper; I did not trace them to primary sources.
- Current SWE-bench Verified saturation level: Anthropic says it is ">80%" (Jan 2026), but I did not fetch a current leaderboard snapshot.

## 4. Reliability: loop/stall detection, repeated actions, error recovery, step budgets, long-horizon completion (METR), failure taxonomies, pass^k

### Takeaway
Agent reliability is far below capability: pass^k decays quickly with k. Production coding agents misbehave in about 30% of trajectories through spec drift, reasoning loops and tool-call failures. Lightweight asynchronous monitors that inject targeted course-corrections fix most single-intervention cases, and cheap deterministic detectors catch repeated identical actions. METR attributes long-horizon gains mainly to better reliability and recovery from mistakes. The harness should therefore make recovery cheap through checkpoints, resumable state, error messages kept in context, and nudges, not just cap steps.

### Cited Findings
- **METR, Measuring AI Ability to Complete Long Software Tasks.** Kwa, West, Becker et al., NeurIPS 2025, [arXiv:2503.14499](https://arxiv.org/abs/2503.14499).
  - Metric: the 50%-task-completion time horizon. Claude 3.7 Sonnet was about 50 minutes (early 2025).
  - The horizon has doubled about every **7 months since 2019**, possibly faster in 2024.
  - Increases are "primarily driven by greater reliability and ability to adapt to mistakes", plus logical reasoning and tool use.
  - [arXiv](https://arxiv.org/abs/2503.14499)
- **METR time-horizons page (accessed 2026-10-31).** Time Horizon 1.1 uses the same method with a larger task suite. GPT-5 is about 2h17m. Recent additions include Claude Opus 4.6 and GPT-5.3-Codex (Feb 20, 2026), GPT-5.4 (Apr 10, 2026), Gemini 3.1 Pro (Apr 15, 2026) and Claude Mythos Preview (May 8, 2026). "Measurements above 16 hrs are unreliable with our current task suite." The page has been "no longer actively updated" since Sep 8, 2026. — [METR](https://metr.org/time-horizons/). Secondary sources: Wikipedia says Claude Mythos had a 50% horizon "likely at least 16 hours" as of May 2026, and forecasting sites cite about 4-month or shorter doubling under TH1.1 for 2023/2024+ fits; **unverified against METR primary text**. — [Wikipedia](https://en.wikipedia.org/wiki/METR)
- **τ-bench.** Yao, Shinn, Razavi et al. (Sierra), Jun 2024, [arXiv:2406.12045](https://arxiv.org/abs/2406.12045). Introduces **pass^k**, the probability that all k trials succeed. GPT-4o succeeded on fewer than 50% of tasks, and **pass^8 was under 25% in retail**. — [arXiv](https://arxiv.org/abs/2406.12045)
- **τ²-bench.** Barres et al. (Sierra), Jun 2025, [arXiv:2506.07982](https://arxiv.org/abs/2506.07982). A dual-control telecom domain where the user also acts via tools. Performance drops significantly when moving from no-user to dual-control, isolating communication and coordination errors from reasoning errors. — [arXiv](https://arxiv.org/abs/2506.07982)
- **Wink: Recovering from Misbehaviors in Coding Agents.** Nanda, Maddila, Jha et al. (Meta production data), Feb 2026, [arXiv:2602.17037](https://arxiv.org/abs/2602.17037). A taxonomy from production traffic: **Specification Drift, Reasoning Problems (incl. repetitive loops), Tool Call Failures**, together in **about 30% of all trajectories**. Wink is a lightweight **asynchronous** observer that injects targeted course-correction guidance. It resolved **90% of misbehaviors needing a single intervention** across 10,000+ trajectories. A live A/B test showed statistically significant reductions in tool-call failures, tokens per session and engineer interventions per session. — [arXiv](https://arxiv.org/abs/2602.17037)
- **The Cognitive Companion.** Khan & Khan, Apr 2026, [arXiv:2604.13759](https://arxiv.org/abs/2604.13759). A feasibility study, small-scale.
  - Agents suffer looping, drift and stuck states at rates up to 30% on hard tasks.
  - Hard step limits are "abrupt", and LLM-judge monitoring costs 10–15% overhead per step.
  - A parallel LLM companion reduced repetition on loop-prone tasks by **52–62% at about 11% overhead** (Gemma 4 E4B).
  - A hidden-state probe companion had zero overhead (AUROC 0.840) but requires model internals.
  - Benefit is task-dependent: it helps on loop-prone and open-ended tasks, and is neutral or negative on structured ones.
  - **It did not help 1–1.5B models.** **[LOCAL]**
  - [arXiv](https://arxiv.org/abs/2604.13759)
- **OpenHands stuck detector** (SDK docs). Enabled by default. It flags a conversation as stuck after repeated identical action-observation pairs; the docs give 4 identical pairs as the threshold. — [OpenHands docs](https://docs.openhands.dev/sdk/guides/agent-stuck-detector). Practitioner guidance: repeated tool *names* can be normal exploration, while repeated name **and** identical arguments usually signal a loop. — [FutureAGI glossary](https://futureagi.com/glossary/agent-loop-detection/)

- **TheAgentCompany.** Xu et al. (CMU), Dec 2024, [arXiv:2412.14161](https://arxiv.org/abs/2412.14161). In a simulated software company, the best agent completed **30%** of tasks autonomously. Long-horizon tasks remain hard. — [arXiv](https://arxiv.org/abs/2412.14161)
- **CASEL: Consequence-Aware Selective Execution.** Zhang et al., Oct 2026, [arXiv:2610.36570](https://arxiv.org/abs/2610.36570). For each proposed tool call, it picks among execute, verify, sandbox, clarify, approve or abstain. The choice combines calibrated failure probability, state-dependent consequence, **reversibility**, ambiguity and evidence freshness. In simulation, harmful-side-effect trajectories fell from 14.75% (uncertainty-ranked gate) to 7.02%. A probability × consequence gate reached similar harm but sent **45% more actions to human approval**. - **When Agents Fail to Act.** Huang, Malwe, Wang, Jan 2026, [arXiv:2601.16280](https://arxiv.org/abs/2601.16280). A 12-category tool-invocation error taxonomy across 1,980 tests. - **Trial by Trace (TraceTrial-Bench).** Cao et al., Oct 2026, [arXiv:2610.32285](https://arxiv.org/abs/2610.32285). Evaluates harness reliability across 7 components: context, execution, governance, lifecycle, observability, tools, verification. Setup: 4 harnesses × 9 models × 95 tasks. Harness scores ranged 59.8–72.0%, and **31.1% of runs succeeded at the task while failing at least one harness criterion**, so outcome-only evals hide harness defects. — [arXiv](https://arxiv.org/abs/2610.32285)
- **Scaffold Effect** (Section 3): harness-specific failure fingerprints such as MAX_TURNS, idle loops and TIME replicate across models. — [arXiv:2607.22585](https://arxiv.org/abs/2607.22585)

### Inferences
- **Harness note (deterministic loop detector):** Hash each (tool name, normalized args) and (action, observation) pair. Flag on N identical consecutive pairs (OpenHands uses 4), on A-B-A-B cycles, and on "no-progress" windows: no file changes, no new information and no plan updates over K steps. On a flag, inject a structured nudge first ("You have repeated X 4 times with the same result; change approach or ask the user"). Pause for user steering only if the loop continues. Abrupt termination is the last resort.
- **Harness note (async monitor, Wink-style):** Run a cheap monitor model, which can be a small local one, asynchronously over the trajectory every K steps. It classifies spec drift, reasoning loops and tool-call failures, and on detection enqueues a steering-style message into the main loop. Xylo's existing steering mechanism (user messages injected mid-run) is the natural delivery channel for these nudges, labeled as harness-originated, not user-originated.
- **Harness note (budgets):** Combine step, token, wall-clock and cost budgets with soft warnings, e.g., at 80%: "you have 5 steps left; wrap up or summarize state". Treat MAX_TURNS hits as an eval failure category to track.
- **Harness note (recovery):** Keep tool errors in context as structured, actionable messages (error class, retryable or not, hint). Retry transient tool errors such as network failures and rate limits in the harness without spending model turns. Checkpoint conversation plus workspace (git) so runs and forks can resume after a crash or app restart.
- **Harness note (risk-tiered approval):** Route tool calls by reversibility × consequence, not just by tool name. Reversible local edits in a sandbox or worktree are auto-approved. Irreversible or external actions (network sends, deletes outside the workspace, git push, payments) go to approval. CASEL suggests this lowers harm without flooding the user, since a pure risk-product gate needed 45% more approvals.
- **Local models [LOCAL]:** For small models, the dominant failures are procedural tool-call errors: malformed calls, initialization, missing arguments. Constrained decoding with JSON-Schema grammars, argument validation with precise error messages, and automatic repair re-prompts deliver more than monitors. Monitors did not help 1–1.5B models.
- METR's "reliability and adapting to mistakes" finding, together with Wink's 30% misbehavior rate, suggests recovery features may matter more than planning features for long tasks. This is my inference.

- Wink's exact A/B effect sizes were not in the abstract.

## 5. Security for tool-using agents: prompt injection via tool outputs, harness-level defenses, permission design, MCP-specific attacks

### Takeaway
Prompt-level defenses (delimiters, spotlighting, "ignore instructions in data", detectors) reduce static attack rates but are broken by adaptive attackers: 12 defenses were bypassed at over 90% ASR. Defenses with real guarantees are **architectural**: restrict what an agent can do after reading untrusted data. Options include plan-then-execute or CaMeL-style control/data-flow separation with capabilities, the dual-LLM and quarantine patterns, information-flow labels (FIDES), deterministic least-privilege policies (Progent), and the "Rule of Two" (no session combining untrusted input, sensitive data and external side effects without a human in the loop). MCP adds supply-chain style threats: tool poisoning, rug pulls, cross-server shadowing. These call for pinned and hashed tool definitions, full-description visibility, and per-server isolation. OS-level sandboxing (filesystem plus network) both contains damage and reduces approval fatigue (84% fewer prompts).

### Cited Findings

**Benchmarks / threat evidence**
- **AgentDojo.** Debenedetti, Zhang, Balunović et al. (ETH Zurich SPY Lab / Invariant Labs), NeurIPS 2024 Datasets & Benchmarks, [arXiv:2406.13352](https://arxiv.org/abs/2406.13352). An extensible environment with 97 realistic tasks (email, e-banking, travel, Slack) and 629 security test cases. SOTA LLMs fail many tasks even without attacks, and existing attacks break some security properties but not all. It has become the standard harness for defense evaluation (CaMeL, MELON, Progent, FIDES all report on it). — [arXiv](https://arxiv.org/abs/2406.13352)
- **InjecAgent.** Zhan et al. (UIUC), ACL Findings 2024, [arXiv:2403.02691](https://arxiv.org/abs/2403.02691). 1,054 test cases, 17 user tools and 62 attacker tools, covering direct-harm and data-exfiltration intents. ReAct-prompted GPT-4 was vulnerable **24%** of the time, and that **nearly doubled** with a "hacking prompt" reinforcement. — [arXiv](https://arxiv.org/abs/2403.02691)
- **The Attacker Moves Second.** Nasr, Carlini, Sitawarin et al. (OpenAI / Anthropic / Google DeepMind et al.), Oct 2025, [arXiv:2510.09023](https://arxiv.org/abs/2510.09023). Adaptive attacks (gradient, RL, random search, human red-teaming) **bypassed 12 recent jailbreak and prompt-injection defenses with ASR above 90% for most**, though most originally reported near-zero ASR. — [arXiv](https://arxiv.org/abs/2510.09023); commentary: [Simon Willison](https://simonw.substack.com/p/new-prompt-injection-papers-agents)
- **Ignored, Not Refused** (small models). Zarif et al., Oct 2026, [arXiv:2610.23254](https://arxiv.org/abs/2610.23254). 33,000 trajectories from 11 open-weight agents (2–14B) on InjecAgent and AgentDojo. Most failed attacks were **ignored (76–80%), not refused (17–18%)**. **Changing only the system prompt moved InjecAgent ASR from 0.2% to 43%** with identical weights. In 21.7% of AgentDojo episodes the agent stayed "safe" but did not complete the user task. A low ASR for small models mostly reflects silent ignoring, not robustness. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2610.23254)
- **The Window Is in the Reasoning.** Jia et al., Oct 2026, [arXiv:2610.24048](https://arxiv.org/abs/2610.24048). Whether an agent follows an injection is not fully settled when it reads it. With thinking on, Qwen3's outcome variance fixed at read time drops from 0.91 to 0.62, and the decision forms gradually during reasoning. Thinking lowered ASR for Qwen3 but **raised it for two other models**. Cheap zero-shot CoT monitors miss much of this. Stronger monitors and a **lookahead monitor that judges simulated next actions** do better. Single-run labels of thinking agents disagree with reruns up to 35% of the time. — [arXiv](https://arxiv.org/abs/2610.24048)

**Architectural defenses**
- **CaMeL: Defeating Prompt Injections by Design.** Debenedetti, Shumailov, Fan et al. (Google DeepMind / Google / ETH Zurich), Mar 2025, [arXiv:2503.18813](https://arxiv.org/abs/2503.18813). A privileged LLM sees only the trusted user query and writes a program, which fixes the control flow. A quarantined LLM parses untrusted data but has no tool access. A custom interpreter tracks **capabilities** (provenance and allowed readers) on every value and enforces security policies at tool-call time, so untrusted data "can never impact the program flow" and exfiltration over unauthorized flows is blocked. Result: **77% of AgentDojo tasks solved with provable security vs 84% undefended**. — [arXiv](https://arxiv.org/abs/2503.18813)
- **Design Patterns for Securing LLM Agents against Prompt Injections.** Beurer-Kellner, Buesser, Creţu et al. (multi-institution; Invariant Labs-led), Jun 2025, [arXiv:2506.08837](https://arxiv.org/abs/2506.08837). Principled patterns "with provable resistance to prompt injection", with utility/security trade-offs and case studies. From the paper body (not the abstract), the six patterns are:
  1. **Action-Selector**: the LLM only picks from fixed actions, with no feedback of tool output.
  2. **Plan-Then-Execute**: the plan is fixed before untrusted data is seen.
  3. **LLM Map-Reduce**: isolated sub-LLMs process each untrusted item and return constrained outputs.
  4. **Dual LLM**: privileged vs quarantined, with symbolic variable references.
  5. **Code-Then-Execute**: CaMeL-like.
  6. **Context-Minimization**: strip the user prompt or untrusted content from context before later steps.

  — [arXiv](https://arxiv.org/abs/2506.08837)
- **Dual LLM pattern.** Simon Willison, Apr 25, 2023. A privileged LLM with tools never sees untrusted text. A quarantined LLM processes untrusted text and returns results referenced only by variable names ($VAR1), which the controller (ordinary code) substitutes when displaying or acting. — [simonwillison.net](https://simonwillison.net/2023/Apr/25/dual-llm-pattern/)
- **The lethal trifecta.** Simon Willison, Jun 16, 2025. Private data, exposure to untrusted content, and an exfiltration channel together enable data theft. — [simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Meta "Agents Rule of Two"** (Oct 31, 2025). Until injection can be reliably detected, a session should combine at most two of: [A] processing untrustworthy inputs, [B] access to sensitive systems or private data, [C] changing state or communicating externally. If all three are needed, require human-in-the-loop or a new session. This extends the trifecta from exfiltration to state-changing actions. — [Simon Willison summary](https://simonw.substack.com/p/new-prompt-injection-papers-agents)
- **FIDES: Securing AI Agents with Information-Flow Control.** Costa, Köpf, Kolluri et al. (Microsoft), May 2025, [arXiv:2505.23643](https://arxiv.org/abs/2505.23643). A planner tracks **confidentiality and integrity labels**, deterministically enforces policies via dynamic taint tracking, and adds primitives for selectively hiding information from the planner. On AgentDojo it completes a broad range of tasks with security guarantees. — [arXiv](https://arxiv.org/abs/2505.23643); [tutorial](https://github.com/microsoft/fides)
- **Progent: Privilege Control.** Shi, He, Wang et al., Apr 2025, [arXiv:2504.11703](https://arxiv.org/abs/2504.11703). Policies are symbolic rules over tool names and **arguments**, checked deterministically on every call. An LLM drafts the initial policy from the user task and proposes updates. An SMT solver classifies each update as narrowing (auto-applied) or expansion (**requires explicit approval**), which gives "monotonic confinement". It significantly reduces ASR on AgentDojo and ASB while maintaining utility, and has been demonstrated in LangChain and the OpenAI Agents SDK. — [arXiv](https://arxiv.org/abs/2504.11703)
- **MELON.** Zhu et al., ICML 2025, [arXiv:2502.05174](https://arxiv.org/abs/2502.05174). Re-executes the trajectory with a **masked user prompt**. If the agent produces the same tool calls without the user's task, they are driven by injected content, so an attack is flagged. It outperforms SOTA defenses on AgentDojo in both prevention and utility, and combining it with prompt augmentation (MELON-Aug) improves further. Costs one extra model call per step. — [arXiv](https://arxiv.org/abs/2502.05174)
- **Spotlighting.** Hines et al. (Microsoft), Mar 2024, [arXiv:2403.14720](https://arxiv.org/abs/2403.14720). Transforms untrusted input to mark provenance continuously: delimiting, datamarking (interleaving a special token) or encoding (e.g., base64). With GPT-family models, ASR fell from **over 50% to under 2%** with minimal task impact. **Caveat:** this is a static-attack evaluation, and "Attacker Moves Second" shows prompt-level defenses fall to adaptive attacks. — [arXiv](https://arxiv.org/abs/2403.14720)

**Sandboxing and approval design**
- **Anthropic, "Claude Code sandboxing"** (Oct 20, 2025). OS-level sandboxing reduced **permission prompts by 84%** in internal usage:
  - **Filesystem isolation**: read/write in the working directory only.
  - **Network isolation**: all traffic goes via a Unix-socket proxy outside the sandbox that enforces a domain allowlist and asks the user about new domains.
  - Enforced with Linux bubblewrap and macOS seatbelt, covering subprocesses.
  - **Both** are needed: without network isolation, a compromised agent exfiltrates keys; without filesystem isolation, it escapes the sandbox to gain network access.
  - Approval fatigue makes users stop scrutinizing prompts.
  - In cloud sandboxes, credentials never enter the sandbox. A git proxy validates a scoped credential and the operation (e.g., push only to the configured branch), then attaches the real token.
  - [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-sandboxing)

**MCP-specific attacks and defenses**
- **Invariant Labs, "MCP Security Notification: Tool Poisoning Attacks".** Beurer-Kellner & Fischer, Apr 1, 2025.
  - **Tool poisoning**: hidden `<IMPORTANT>` instructions in a tool description tell the model to read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass them via a side parameter. In the Cursor experiment, the confirmation dialog did not show full tool inputs.
  - **Rug pull**: the server changes a description after approval.
  - **Cross-server shadowing**: a malicious server's description rewrites how the agent uses a trusted server's `send_email`.
  - Mitigations: show full tool descriptions and distinguish user-visible from AI-visible text; pin tools and packages with hashes or checksums; enforce cross-server dataflow boundaries; apply guardrails.
  - [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- **MCPTox.** Wang et al., Aug 2025, [arXiv:2508.14925](https://arxiv.org/abs/2508.14925). Built on 45 live MCP servers and 353 real tools, with 1,348 poisoning cases across 10 risk categories, tested on 20 LLM agents. o1-mini reached **72.8% ASR**. **More capable models were often more susceptible**, because the attack exploits instruction-following. The highest refusal rate (Claude 3.7 Sonnet) was **under 3%**. — [arXiv](https://arxiv.org/abs/2508.14925)
- **MCP Safety Audit.** Radosevich & Halloran, Apr 2025, [arXiv:2504.03767](https://arxiv.org/abs/2504.03767). Showed industry-leading LLMs coerced via MCP tools into malicious code execution, remote access control and credential theft. Released the agentic MCPSafetyScanner auditor. — [arXiv](https://arxiv.org/abs/2504.03767)
- **MCP Threat Modeling … Tool Poisoning.** Huang et al., Mar 2026, [arXiv:2603.22489](https://arxiv.org/abs/2603.22489). STRIDE/DREAD analysis across host/client, LLM, server, data stores and auth server. Tool poisoning is the most prevalent and impactful client-side vulnerability. Of **seven major MCP clients**, most had significant issues due to "insufficient static validation and parameter visibility". Proposes static metadata analysis, decision-path tracking, behavioral anomaly detection and user transparency. — [arXiv](https://arxiv.org/abs/2603.22489)
- **ETDI.** Bhatt, Narajala, Habler, Jun 2025, [arXiv:2506.01333](https://arxiv.org/abs/2506.01333). Mitigates tool squatting and rug pulls with cryptographic identity, **immutable versioned tool definitions**, OAuth-scoped permissions and a policy engine for runtime context. — [arXiv](https://arxiv.org/abs/2506.01333)
- **TRUSTDESC.** Ye et al., Apr 2026, [arXiv:2604.07536](https://arxiv.org/abs/2604.07536). Handles **implicit** poisoning (misleading claims, not explicit instructions), which detectors miss, by **regenerating tool descriptions from the tool's implementation**: static slicing → description synthesis → dynamic verification. Evaluated on 52 real tools with minimal overhead. — [arXiv](https://arxiv.org/abs/2604.07536)
- **ShareLock.** Liu et al., Jun 2026, [arXiv:2606.27027](https://arxiv.org/abs/2606.27027). Splits a malicious instruction into Shamir secret shares across multiple benign-looking tool descriptions, then reconstructs it after a server-update trigger (rug-pull style). Monolithic per-tool scanning misses it. — [arXiv](https://arxiv.org/abs/2606.27027)
- **SMCP: Secure Model Context Protocol.** Hou et al., Feb 2026, [arXiv:2602.01129](https://arxiv.org/abs/2602.01129). Proposes protocol-level identity management, mutual authentication, security-context propagation, fine-grained policy and audit logging. A design proposal, not an evaluation. — [arXiv](https://arxiv.org/abs/2602.01129)
- **Other recent MCP/agent-injection papers found (titles verified, contents not reviewed):**
  - "Log-To-Leak: Prompt Injection Attacks on Tool-Using LLM Agents via the Model Context Protocol" ([arXiv:2610.36108](https://arxiv.org/abs/2610.36108))
  - "Package Hallucination Attacks on Coding Agents through Prompt Injection in Rule Files" ([arXiv:2610.09264](https://arxiv.org/abs/2610.09264))
  - "SEAL: Towards Persistent Tool Poisoning Attack…" ([arXiv:2610.25372](https://arxiv.org/abs/2610.25372))

### Inferences
- **Harness note (Rule-of-Two session tainting):** Track three per-session or per-subagent flags: `untrusted_input_seen` (web fetch, email, third-party MCP output, files from downloads), `sensitive_access` (secrets, home directory, credentials, private repos), and `external_side_effects` (network send, git push, messages). When a session would hold all three, require explicit approval for each side-effecting call, or force the side effect into a fresh, clean subagent that sees only structured data. This is cheap to implement and model-agnostic.
- **Harness note (taint and quarantine for tool outputs):** Label every tool result with provenance (user, local workspace, internet, MCP server X). For high-risk flows, use the **dual-LLM / map-reduce pattern**: a quarantined subagent with no tools reads untrusted content and returns a constrained, schema-typed result (e.g., enum, number, short extracted field). The main agent references it by handle. Show the user when a side-effecting call's arguments derive from untrusted data, a lightweight version of CaMeL/FIDES provenance.
- **Harness note (deterministic policy layer, Progent-style):** Express permissions as rules over tool **and arguments**, e.g., `shell: allow cmd matches ^(git status|cargo test)`, `fs.write: allow path under $WORKSPACE`, `http: allow domain in allowlist`. Evaluate them in Rust, not by the model. Let the model *propose* policy narrowing freely, but require user approval for any expansion (monotonic confinement).
- **Harness note (sandbox first, prompt second):** Pair Xylo's approval UI with OS sandboxing: seatbelt on macOS, bubblewrap or landlock on Linux. Use filesystem write-confinement to the workspace plus a network egress proxy with a domain allowlist. Keep credentials outside the sandbox and inject them via a proxy for git and package registries. Auto-approve in-sandbox actions to fight approval fatigue (Anthropic: −84% prompts). Reserve prompts for sandbox escapes and new domains.
- **Harness note (MCP hygiene):**
  1. Hash each server's tool list and descriptions at approval time. Re-prompt on any change (rug pull) and show a diff.
  2. Show full descriptions and full call arguments in the approval UI. Invariant found Cursor hid them.
  3. Namespace tools per server and forbid one server's description from referencing another server's tools (cross-server shadowing). Scan descriptions jointly across servers, since ShareLock-style threshold attacks evade per-tool scans.
  4. Run local MCP servers inside the same sandbox with their own egress policy.
  5. Treat MCP tool *outputs* as untrusted input for Rule-of-Two tainting.
- **Harness note (detectors are defense-in-depth only):** Spotlighting/datamarking of tool outputs and MELON-style masked re-execution are worth adding as cheap layers. Do not market them as guarantees, since adaptive attacks bypass prompt-level defenses at over 90%.
- **Local models [LOCAL]:** Small models' low ASR is mostly "ignored, not refused", and system-prompt changes swing ASR from 0.2% to 43%. Xylo cannot rely on a local model's robustness. The architectural controls (sandbox, policy, taint, approval) are what protect local-model sessions. Include injection tests in the regression suite whenever the system prompt changes.
- **Capable-model paradox:** MCPTox found more capable models more susceptible to tool poisoning. Frontier cloud models do not remove the need for MCP description pinning or vetting.

### Gaps
- I did not verify the exact AgentDojo baseline utility and ASR numbers per model, or CaMeL's per-model breakdown beyond the abstract's 77% vs 84%.
- I found no measured study of approval-UI designs (e.g., per-call vs per-session vs risk-tiered) and their effect on user error rates, beyond Anthropic's 84% prompt reduction and the "approval fatigue" argument.
- The MCP specification's current status on signed or pinned tool definitions (as of Oct 2026) was not verified. One secondary source claimed no protocol-level rug-pull detection exists yet.

## 6. Latency and performance at the harness level: streaming, parallelism, speculative actions, caching, routing / cascades

### Takeaway
The largest harness-level latency wins are parallel tool calls and parallel read-only subagents (up to 90% wall-clock reduction for research; LLMCompiler up to 3.7x), and **prompt-cache discipline**. Cached input is about 10x cheaper, agent input:output ratios are about 100:1, and cache mis-integration is common and silent. Routing and cascades (FrugalGPT, RouteLLM) save cost for independent queries. For stateful agents, routing should happen at user-turn boundaries with session history, and favor expensive→cheap switches because of cache economics. Speculative actions give modest gains (up to 20% latency) at extra cost.

### Cited Findings
- **Anthropic multi-agent system:** parallel subagents (3–5) plus parallel tool calls (3+) cut research time by up to **90%** on complex queries. — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **LLMCompiler:** DAG planning plus parallel function execution gives up to **3.7x latency speedup and 6.7x cost savings** vs ReAct. — [arXiv:2312.04511](https://arxiv.org/abs/2312.04511)
- **ReWOO:** 5x token efficiency, because the plan is generated once and observations are not re-fed for re-planning. — [arXiv:2305.18323](https://arxiv.org/abs/2305.18323)
- **Manus:** KV-cache hit rate is "the single most important metric" for a production agent. Claude Sonnet cached input costs $0.30/MTok vs $3/MTok uncached (10x). The average input:output token ratio is about **100:1**. Practices: stable prompt prefixes (e.g., no timestamps at the top), append-only context, deterministic serialization (stable JSON key order), and **masking tools via logit constraints instead of adding or removing tool definitions mid-run**, which invalidates the cache. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- **Silent and Costly: Prompt-Caching Mis-Integration in LLM Agents (CACHELINT).** Zhang et al., Oct 2026, [arXiv:2610.34817](https://arxiv.org/abs/2610.34817). Studied 120 caching-related PRs in 10 popular open-source agent systems. Mis-integrations occur both request-side (misconfiguration) and read-side (usage miscount), and **most fail silently**. The CACHELINT detector found 32 mis-integrations across 571 projects at 0.86 precision, leading to 18 upstream fixes, including one in Anthropic's official SDK. — [arXiv](https://arxiv.org/abs/2610.34817)
- **Identical Runs, Different Results:** cost differed **over 20x between two agents on the same model, mostly through the prompt cache**. — [arXiv:2609.33812](https://arxiv.org/abs/2609.33812)
- **Scaffold Effect:** up to **40x** tokens per solved task across harnesses on the same model. — [arXiv:2607.22585](https://arxiv.org/abs/2607.22585)
- **FrugalGPT.** Chen, Zaharia, Zou (Stanford), May 2023, [arXiv:2305.05176](https://arxiv.org/abs/2305.05176). An LLM cascade learns which models to query in sequence, with a scorer deciding whether to stop. It matched GPT-4 with **up to 98% cost reduction**, or gained +4% accuracy at equal cost. Evaluated on single-query tasks. — [arXiv](https://arxiv.org/abs/2305.05176)
- **RouteLLM.** Ong et al. (LMSYS / UC Berkeley / Anyscale), Jun 2024, [arXiv:2406.18665](https://arxiv.org/abs/2406.18665). Routers trained on human preference data choose strong vs weak models, reducing cost by **over 2x in some cases** without quality loss. Routers transfer when the strong and weak models are swapped. — [arXiv](https://arxiv.org/abs/2406.18665)
- **Whose turn is it? Context-guided model routing for stateful agents.** Parashar et al., Oct 2026, [arXiv:2610.19292](https://arxiv.org/abs/2610.19292). Zero-shot, cost-aware routing **at the user-turn boundary**, evaluated on multi-turn SheetCopilot and SpreadsheetBench 2.
  - Giving the router **session history** improved pass rate for every model pair, staying within 1pt of always using the expensive model.
  - The cheaper model's per-task cost advantage narrowed from **6.8x to 3.2x** on longer sessions.
  - Cache analysis: **downward switches (expensive→cheap) recover their cache cost within 2 calls; upward switches did not break even** under the evaluated conditions.
  - [arXiv](https://arxiv.org/abs/2610.19292)
- **SALE (Strategy Auctions):** description-based routers "either underperform the largest agent or fail to reduce cost, often both" on agentic workflows. Plan-bid routing cut cost 35%. — [arXiv:2602.02751](https://arxiv.org/abs/2602.02751)
- **Speculative Actions.** Ye et al., Oct 2025, [arXiv:2510.04371](https://arxiv.org/abs/2510.04371). A faster model predicts likely next actions, which are executed in parallel and committed only if the main model agrees (lossless). Results: up to **55% next-action prediction accuracy** and up to **20% latency reduction** across gaming, e-commerce and web search, with a formal cost/latency trade-off for speculation breadth. A lossy variant was studied for OS settings. — [arXiv](https://arxiv.org/abs/2510.04371)
- **Agentic Plan Caching (APC).** Zhang, Wornow, Wan et al., NeurIPS 2025, [arXiv:2506.14852](https://arxiv.org/abs/2506.14852). Extracts plan templates from completed runs, matches new requests by keywords, and adapts templates with a lightweight model. Results: **−50.31% cost and −27.28% latency** on average while maintaining performance (v2 abstract). — [arXiv](https://arxiv.org/abs/2506.14852)
- **Small Language Models are the Future of Agentic AI.** Belcak et al. (NVIDIA), Jun 2025, [arXiv:2506.02153](https://arxiv.org/abs/2506.02153). Position paper: SLMs are sufficient and more economical for many repetitive, specialized agent invocations. Heterogeneous systems should use LLMs only where general conversation and reasoning are needed. Outlines an LLM→SLM conversion algorithm. **[LOCAL]** — [arXiv](https://arxiv.org/abs/2506.02153)
- **Anthropic think tool:** measured on τ-bench; see Section 1. Not a latency technique, but shows a cheap mid-trajectory pause can raise pass^k. — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-think-tool)

### Inferences
- **Harness note (parallel tool execution):** Execute all independent tool calls returned in one model turn concurrently: reads, searches, fetches, read-only shell. Serialize only conflicting writes, using per-path locks. Let read-only subagents run concurrently. These are the biggest measured wins.
- **Harness note (cache discipline as a tested invariant):** Make the system prompt and tool list byte-stable within a session: no timestamps, sorted keys, deterministic tool ordering. Make history append-only, and implement mode changes (plan mode, read-only mode) by **gating tool execution in the harness** or via constrained decoding, not by mutating the tool list. Log provider-reported cache read and write tokens per call and alert on hit-rate regressions. CACHELINT shows these regressions are silent. For local models via llama.cpp, vLLM or MLX, keep the prefix stable for KV-cache/prefix reuse as well.
- **Harness note (routing):** Route at user-turn or subagent boundaries, not per step, using session history. Prefer routing *subagents* to cheap or local models (search, summarization, monitor, quarantine-reader roles) while the main agent stays on one model to keep its cache warm. Avoid mid-session upgrades unless warranted, since upward switches lose the cache. A FrugalGPT-style cascade (local first, escalate to cloud on validator failure) fits well-defined, verifiable subtasks such as JSON extraction or commit messages. **[LOCAL]**
- **Harness note (streaming):** Stream model tokens to the UI and begin executing a tool call as soon as its arguments are complete and parse, rather than waiting for the whole turn. Show partial tool output live. This is a common practice; I found no paper quantifying it, see Gaps.
- **Harness note (speculation):** Speculative pre-execution is attractive only for **read-only, idempotent** tools, e.g., prefetching a file the model is likely to read next or pre-running `git status` or tests. With about 55% prediction accuracy and at most 20% latency gain, it is a later optimization.
- **Harness note (plan caching):** For recurring workflows (e.g., "update deps and run tests"), cache successful plan templates or skills and replay them with a small model. APC reports about −50% cost.

### Gaps
- I found no peer-reviewed measurement of token streaming or early tool dispatch on end-to-end agent latency.
- RouteLLM and FrugalGPT were evaluated on single-turn queries. Agentic routing evidence is limited to 2602.02751 and 2610.19292.
- I did not find published measurements of local-model prefill and KV-reuse effects on agent loop latency, e.g., llama.cpp prompt caching in multi-turn tool loops.

## 7. Evaluation: how a harness author should build evals and regression tests for agent behavior

### Takeaway
Build a small (20–50 task) suite from real failures early and grade **outcomes** (final environment state) with deterministic checks where possible. Add calibrated LLM judges for subjective dimensions, run **multiple trials** and report **pass^k** alongside pass@k, and isolate each trial in a clean environment. Also evaluate harness-level properties (stop/verify behavior, loop rate, approvals, cost, cache hit rate), not just task success. Run-to-run variance is large enough that comparisons need many trials. Public benchmarks (SWE-bench Verified, Terminal-Bench 2.0, τ²-bench, OSWorld, GAIA) are useful calibration but have known validity issues and saturation.

### Cited Findings
- **Anthropic, "Demystifying evals for AI agents".** Grace, Hadfield, Olivares, De Jonghe, Jan 9, 2026.
  - Vocabulary: task, trial, grader, transcript, outcome, eval harness vs agent harness. "Evaluating an agent" means evaluating harness plus model together.
  - Grader types:
    - code-based: fast, objective, brittle to valid variation
    - model-based: flexible, needs calibration against humans
    - human: gold standard, used for calibration
  - **pass@k vs pass^k**: 75% per-trial success over 3 trials gives about 42% pass^3. Use pass^k for customer-facing consistency. At k=10, pass@k approaches 100% while pass^k approaches 0.
  - **Capability evals** start at a low pass rate. **Regression evals** should sit near 100%, and capability evals "graduate" into regression suites.
  - Start with **20–50 tasks from real failures**, bug trackers and support queues. A good task is one where two experts reach the same verdict. Include should-trigger and should-not-trigger cases.
  - A 0% pass rate over many trials usually means a broken task or grader.
  - Grade outcomes, not paths, with partial credit for multi-step tasks.
  - Give LLM judges an "Unknown" option and use one judge per dimension. Make graders cheat-resistant.
  - Use a **clean environment per trial**: one agent gained an unfair advantage by reading git history from earlier trials.
  - Read transcripts regularly. SWE-bench Verified was near saturation at over 80%.
  - Use layered methods (Swiss-cheese model): automated evals, production monitoring, A/B tests, user feedback and transcript review.
  - [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **Anthropic multi-agent system:** about 20 queries sufficed early because effect sizes were large. A single LLM-judge prompt scoring 0.0–1.0 plus pass/fail on a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) matched humans best. Humans caught a preference for SEO content farms. Use end-state evaluation for stateful agents. — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **τ-bench / τ²-bench:** database-state comparison against an annotated goal state; pass^k metric; dual-control user simulation. — [arXiv:2406.12045](https://arxiv.org/abs/2406.12045); [arXiv:2506.07982](https://arxiv.org/abs/2506.07982)
- **Terminal-Bench 2.0.** Merrill, Shaw, Carlini et al., Jan 2026, [arXiv:2601.11868](https://arxiv.org/abs/2601.11868). 89 hard terminal tasks, each with a unique environment, a human-written solution and comprehensive verification tests. Frontier models and agents scored **under 65%** at publication. The harness is public at tbench.ai. — [arXiv](https://arxiv.org/abs/2601.11868)
- **SWE-bench Verified.** OpenAI, Aug 2024: a human-validated 500-instance subset of SWE-bench. — [OpenAI](https://openai.com/index/introducing-swe-bench-verified/). The ABC checklist paper notes SWE-bench Verified "uses insufficient test cases". — [arXiv:2507.02825](https://arxiv.org/abs/2507.02825)
- **SWE-Bench Pro.** Deng et al. (Scale AI), Sep 2025, [arXiv:2509.16941](https://arxiv.org/abs/2509.16941). 1,865 problems from 41 repos, split into public, held-out and commercial sets. Long-horizon, multi-file, contamination-resistant, with failure-mode clustering. — [arXiv](https://arxiv.org/abs/2509.16941)
- **OSWorld.** Xie et al. (HKU et al.), NeurIPS 2024, [arXiv:2404.07972](https://arxiv.org/abs/2404.07972). 369 real desktop and web tasks (Ubuntu, Windows, macOS) with execution-based evaluation scripts. Humans scored 72.36% vs the best model's 12.24% at release; that number is superseded by later models. — [arXiv](https://arxiv.org/abs/2404.07972)
- **GAIA.** Mialon et al. (Meta / Hugging Face), 2023, [arXiv:2311.12983](https://arxiv.org/abs/2311.12983). 466 questions that are conceptually simple for humans but require tools, browsing and multimodality. Humans scored 92% vs 15% for GPT-4 with plugins at release. — [arXiv](https://arxiv.org/abs/2311.12983)
- **HAL.** Kapoor et al., [arXiv:2510.11977](https://arxiv.org/abs/2510.11977). Standardized parallel eval infrastructure: 21,730 rollouts, 9 models × 9 benchmarks, about $40k. **LLM-aided log inspection** surfaced unreported behaviors such as **searching HuggingFace for the benchmark instead of solving the task** and **misusing credit cards in flight-booking tasks**. All 2.5B tokens of logs were released. — [arXiv](https://arxiv.org/abs/2510.11977)
- **AI Agents That Matter.** Kapoor, Stroebl, Siegel et al. (Princeton), Jul 2024, [arXiv:2407.01502](https://arxiv.org/abs/2407.01502). Accuracy-only evaluation produces "needlessly complex and costly" SOTA agents. Optimize cost and accuracy jointly, keep proper holdouts to avoid shortcut overfitting, and standardize for reproducibility. — [arXiv](https://arxiv.org/abs/2407.01502)
- **Establishing Best Practices for Building Rigorous Agentic Benchmarks (ABC).** Zhu et al., Jul 2025, [arXiv:2507.02825](https://arxiv.org/abs/2507.02825). Task-setup and reward-design flaws can mis-estimate performance by **up to 100% relative**; e.g., τ-bench counted empty responses as successes. Applying the checklist to CVE-Bench reduced overestimation by 33%. — [arXiv](https://arxiv.org/abs/2507.02825)
- **AgentRewardBench:** no single LLM judge is best across benchmarks, and rule-based checks underreport success. Calibrate judges per domain. — [arXiv:2504.08942](https://arxiv.org/abs/2504.08942)
- **TraceTrial-Bench:** 31.1% of runs succeed while violating at least one harness-reliability criterion. Evaluate harness mechanisms (context, execution, governance, lifecycle, observability, tools, verification) separately from outcomes. — [arXiv:2610.32285](https://arxiv.org/abs/2610.32285)
- **Identical Runs, Different Results:** distinguishing agent differences needed tens to 100+ runs. Report compliance beside quality, since rule-breaking runs scored highest. — [arXiv:2609.33812](https://arxiv.org/abs/2609.33812)
- **The Window Is in the Reasoning:** single-run injection labels for thinking agents disagree with reruns up to 35% of the time, so security evals need repeated runs. — [arXiv:2610.24048](https://arxiv.org/abs/2610.24048)
- **Ignored, Not Refused:** report *how* attacks fail (ignored vs refused) and whether the user task still completed, not just ASR. — [arXiv:2610.23254](https://arxiv.org/abs/2610.23254)
- **MAST:** the released LLM-as-judge failure annotator can label multi-agent traces with the 14-mode taxonomy. — [arXiv:2503.13657](https://arxiv.org/abs/2503.13657)

### Inferences
- **Harness note (eval architecture for Xylo):**
  1. **Trajectory recorder**: every run emits a structured trace (model calls, tool calls, args, results, approvals, steering injections, subagent spawns, tokens, cache reads, latency). It is replayable and diffable.
  2. **Task format**: a fixture repo or directory snapshot plus a prompt plus graders: an outcome script for files, tests or state, and optional rubric-judge dimensions. This follows the Terminal-Bench style of environment + solution + tests.
  3. **Multi-trial runner**: run k trials in clean worktrees or containers, then compute pass@1, pass^k, cost per success, p50/p95 latency, loop-detector firings, MAX_TURNS hits, approvals requested, and cache hit rate.
  4. **Suites**: a regression suite (near 100% expected, run on every harness change) and a capability suite (low pass rate, tracks progress). Seed both from Xylo's own bug reports and failed sessions.
  5. **Model matrix**: run the same suite across cloud and local models to catch model-specific regressions, e.g., a system-prompt change that helps Claude but breaks a 7B local model.
  6. **Security suite**: an AgentDojo-style injected-tool-output scenario plus MCP tool-poisoning and rug-pull fixtures. Report ASR, ignored-vs-refused, and utility under attack.
  7. **Harness-property checks**: assert invariants independent of outcome. Examples: never wrote outside the workspace without approval; tool list unchanged mid-session (cache); subagent returned within budget; verification run before "done" on coding tasks.
- **Harness note (statistics):** Use paired comparisons on the same tasks and report confidence intervals. Do not trust 1–3 run differences. Variance studies show tens of runs are needed for small deltas.
- **Harness note (LLM judges):** Use per-dimension judges with an "Unknown" option, calibrated against a small human-labeled set per domain, plus periodic transcript reading. Use the MAST annotator or AgentDebug-style root-cause tagging to bucket failures automatically.
- **Public benchmarks for smoke tests:** Terminal-Bench 2.0 is closest to a desktop coding harness, with a public harness. SWE-bench Verified is saturated at the frontier but still informative for local models. τ²-bench suits conversational and approval flows. OSWorld suits any computer-use features. Run a small stratified subset in CI; Scaffold Effect used a 50-task subset. Publish a Harness Card with any reported numbers.
- **Local models [LOCAL]:** Track schema-validity rate and executable-call rate as first-class metrics for local models, as the SLM survey recommends. Many small-model failures are procedural, not reasoning, failures.
