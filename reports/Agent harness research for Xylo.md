# Prune, Validate, Recover: Upgrading Xylo's Harness

Xylo's harness has the most to gain from a short list of deterministic changes, not from new agent architectures. The strongest evidence says to mask stale tool outputs long before the 80% summary trigger (JetBrains found plain observation masking matched LLM summarization on SWE-bench Verified at about half the raw agent's cost ([Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433))), to size every budget from the model's effective rather than advertised window, to validate and repair tool arguments against their schemas before dispatch, to recover from context overflows, max-token cutoffs and repeated identical calls that Xylo currently either fails on or accepts silently, and to keep the system prompt byte-identical across turns so prompt caching keeps paying. Memory needs non-destructive, origin-bound writes and an agent-searchable history more than it needs better embeddings. These changes matter because 2026 studies find the harness moves results for a fixed model by up to 28 points and tokens per solved task by up to 40×. Xylo already does several things the literature recommends (durable checkpoints, exactly-once journaled tool dispatch, incremental summaries, spill-to-file for large outputs, parallel reads, deferred tools, hybrid BM25-plus-embedding memory), so most fixes are local edits in `provider_guard.rs`, `agent_loop/`, `dispatch.rs`, `tools/mod.rs` and `services/memory.rs`. Small local models gain the most: under Xylo's default 8,192-token window, tool schemas and the fixed prompt plausibly consume most of the room before any history arrives, and one 64 KiB tool result (about 16K tokens) is twice the whole window. Cloud models gain most from cache stability, ranked tool search, agent-searchable history and narrowly scoped subagents. Much of the 2026 evidence comes from single-team preprints or vendor-reported numbers, and the report tags every such claim so the roadmap's evidence ratings can be checked.

## Harness design now moves results as much as the model does

Controlled 2026 studies keep finding that the scaffolding around a model changes outcomes about as much as swapping the model itself. A position paper with a controlled grid found **harness-induced variance 7.8× larger than model-induced variance**, with six ranking reversals in nine comparisons [2026 preprint] ([Zhang et al., arXiv 2605.23950](https://arxiv.org/abs/2605.23950)). Running the same models through Goose, OpenCode and OpenHands-SDK changed **tokens per solved task by up to 40×** while pass rates moved only 0–8 points ([Vats & Golev, ICML 2026](https://arxiv.org/abs/2607.22585)), and a pre-registered GAIA comparison saw scaffold choice alone move one model by **28 points**, rejecting the prediction that stronger models are less scaffold-sensitive [2026 preprint] ([Starace, arXiv 2606.08529](https://arxiv.org/abs/2606.08529)). The counterweight is that Claude Code, mini-SWE-agent and OpenCode gave equivalent SWE-bench Verified pass rates within noise while cost per task differed by up to **3×**, a cost set "at the first call" by the system prompt and tool schemas and then multiplied by the step count [2026 preprint] ([Liu & Han, arXiv 2610.04433](https://arxiv.org/abs/2610.04433)); complex harnesses also gave diminishing returns on issue repair as open-weight models strengthened [2026 preprint] ([Hu et al., arXiv 2609.32459](https://arxiv.org/abs/2609.32459)). Read together, the harness mostly buys cost and reliability for frontier models on routine coding, and it also buys accuracy for weaker models and longer, harder tasks. Xylo serves both populations, so it should optimize tokens per solved task and recovery from failure, and it should measure each model separately.

Xylo's native engine already implements much of what this literature recommends. Its loop (`steps()` in `agent_loop/mod.rs`) is linear and ReAct-shaped, checkpoints before and after every tool batch, and dispatches each tool exactly once through a journaled broker, which gives it the resume-from-checkpoint behavior Anthropic recommends for stateful agents ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Read-only calls run up to four at a time while writes serialize behind a per-file `EditLock` (`dispatch.rs`, `MAX_PARALLEL_READS`). Once history passes 80% of the allowance, an LLM summary replaces older history; it is updated incrementally rather than regenerated, and it is checkpointed (`provider_guard.rs`, `summarize`). Tool results over 64 KiB spill to `artifacts/tool-<id>.txt` with a pointer the model can page (`tools/mod.rs`, `model_result`). Anthropic requests carry three cache breakpoints, rarely used tools sit behind `search_tools` and `call_tool`, MCP servers sit behind the `connector_*` tools, and project facts use SQLite FTS5 BM25 fused with optional local embeddings through reciprocal-rank fusion (`services/memory.rs`).

The gaps the architecture notes confirmed sit elsewhere. Nothing prunes context below the 80% trigger. Context overflows and max-token cutoffs are not recovered, and nothing detects stalls or repeated calls. Tool arguments are never checked against their JSON Schemas, and local models without native function calling have no fallback. Facts and learned procedures retrieved per turn change the system prompt, and memory writes cannot supersede earlier facts.

Two reading notes apply throughout. Code locations come from the architecture notes, which read an uncommitted engine that was being edited on 2026-10-31; spot checks the same day found drift of a few lines (`MAX_MODEL_CALLS` at `agent_loop/mod.rs:55`, `fit` at `:400`, `search_tools` at `tools/mod.rs:941`, the 64 KiB `MODEL_BYTES` constant at `tools/mod.rs:1236`), so search by symbol name and treat line numbers as approximate. Evidence carries inline tags that say how far to trust a number:

| Tag | Meaning |

| **[vendor]** | Numbers a company reported about its own product or method, from internal evaluations |
| **[2026 preprint]** | A single-team 2026 arXiv preprint, not peer-reviewed or replicated |

## Context: mask stale tool output long before the 80% summary

### Xylo's default 8K budget is mostly spent before history arrives

Every long-context benchmark since 2023 finds the usable window far smaller than the advertised one. RULER found only half of 17 models claiming 32K+ stayed satisfactory at 32K ([Hsieh et al., COLM 2024](https://arxiv.org/abs/2404.06654)), and its leaderboard rates Llama 3.1 8B as effective to **32K of a claimed 128K** and Mistral 7B v0.2 to **16K of 32K** ([RULER leaderboard](https://github.com/NVIDIA/RULER)). On NoLiMa, where the needle shares few words with the question, 11 of 13 models fell below half their short-context score by 32K, with GPT-4o dropping from 99.3% to 69.7% ([Modarressi et al., ICML 2025](https://arxiv.org/abs/2502.05167)). Du et al. showed that **length alone costs 13.9–85%** of performance even with perfect retrieval, and the loss persisted when the extra tokens were whitespace or masked out of attention ([Du et al., Findings of EMNLP 2025](https://arxiv.org/abs/2510.05381)); Chroma found all 18 models it tested scored better on LongMemEval with a focused ~300-token prompt than with the full ~113K-token one ([Chroma](https://www.trychroma.com/research/context-rot)). The practical rule is that removing tokens beats rearranging them, and that a working window of roughly 8K–32K is realistic for 7–14B local models whatever the model file advertises.

Xylo has no model of the effective window and miscounts the window it does have. Each connection's `ProviderConfig` defaults to 8,192 context and 2,048 output tokens; catalog discovery overwrites these only when the server reports a context field, and the engine has no per-model limit table. Ollama itself defaults to a **4K context on machines with under 24 GiB of VRAM** and recommends at least 64K for agents and coding tools ([Ollama docs](https://docs.ollama.com/context-length)), so a local user can run a 4K server while Xylo budgets for 8K, and Ollama's documentation does not say whether over-length prompts are truncated silently or rejected. Non-OpenAI models are estimated as `o200k × 1.3`, and the provider's reported `input_tokens` is shown in the UI but never used to correct the estimate (`agent_loop/mod.rs`, around `:362–375`). By my rough arithmetic from the notes' byte counts (about 8–9 KB of always-offered tool schemas, about 6 KB of system prompt with skills, and Xylo's rule of schema JSON plus 64 tokens per tool plus 256 tokens of framing), the fixed preamble plausibly takes most of the ~6K tokens left after the default 2,048-token output reserve, before any project instructions (budgeted up to 24 KiB in `prompts/instructions.rs`) or any history. That is an estimate, not a measurement; the `ContextUsage` event already reports the system, tools and messages split and can confirm it on a real local session. Meanwhile one 64 KiB tool result is about 16K tokens, `file_read` returns up to 2,000 lines and 40 KiB by default (`code.rs`), and a subagent may return 64 KB (`subagent.rs`); each cap is fixed regardless of window size, and each alone exceeds an 8K window.

The fix is to make the effective window a first-class number. `ContextBudget` should compute `W_eff` as the minimum of the configured context, the context the local server actually serves (Ollama reports its loaded context, so ask rather than trusting catalog metadata), and a per-family effective-length entry seeded from RULER. Each call's provider-reported input tokens should feed back as a running correction factor per model; this is an engineering inference rather than a published result, though the CACHELINT study warns that usage miscounting is a common silent bug ([Zhang et al., ICSE 2027](https://arxiv.org/abs/2610.34817)). Every fixed cap should then scale from `W_eff`. `MODEL_BYTES` becomes the smaller of 25K tokens (Claude Code's default cap [vendor] ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents))) and roughly 10–15% of `W_eff`; ACON found compressing observations above about **1,024 tokens** gave the best trade-off ([Kang et al., ICML 2026](https://arxiv.org/abs/2510.00615)), and Microsoft's survey of real MCP tools found **56 that overflow a 32K window and 93 that overflow a 16K window in a single call** ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale/)). The `file_read` default window, the subagent return cap, the 24 KiB project-instruction budget and the 8 KiB skills-index budget should follow the same rule, with a target of a fixed preamble at 15–20% of `W_eff` for small windows. That target is a design heuristic from the notes, and IFScale's finding that frontier models reach only 68% accuracy at 500 simultaneous instructions points the same way: keep always-on instructions few ([Jaroslawicz et al., arXiv 2507.11538](https://arxiv.org/abs/2507.11538)).

Overflow should become recoverable, not fatal. Today a provider `context_length_exceeded` maps to `ContextOverflow`, which `retry.rs` treats as non-retryable, and `model_call` has no compact-and-retry path, so the turn fails. The change is to catch `ContextOverflow` once in `model_call`, force compaction to a lower target (around 60%), shrink the calibration factor and retry. Two preprints show why this matters most on small windows. A 176-setting harness study found context management grows more valuable as budgets tighten, mostly by preventing overflow failures [2026 preprint] ([Fan et al., arXiv 2609.20804](https://arxiv.org/abs/2609.20804)). Bud ContextCompact ran a 27B reasoning model in a 49K window and found the main failure without compaction was "a reasoning turn exhausting the room the history left"; compaction raised long-session resolve rates from **41% to 53%**, but only when it triggered early enough to leave that room [2026 preprint] ([arXiv 2610.25516](https://arxiv.org/abs/2610.25516)). Xylo should therefore reserve output plus a reasoning allowance for reasoning models and trigger earlier on small windows, keeping in mind that the desktop UI caps output at a quarter of the context.

### Deterministic masking matches LLM summaries at half the cost

The best-supported first tier of compaction is cheap and deterministic: replace old tool *observations* with placeholders while keeping the agent's own reasoning and actions. JetBrains ran SWE-agent on SWE-bench Verified and compared a 10-turn observation-masking window with LLM summarization ([Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)):

| Model (SWE-bench Verified) | Raw agent | Observation masking | LLM summary |
|---|---|---|---|
| Qwen3-Coder 480B | 53.4%, $1.29 | 54.8%, $0.61 | 53.8%, $0.64 |
| Gemini 2.5 Flash | 32.8%, $0.41 | 35.6%, $0.18 | 36.0%, $0.24 |
| Gemini 2.5 Flash (thinking) | 40.4% | 36.4% | 31.4% |

Summarization made trajectories about **13–15% longer** than masking, and a hybrid of masking first plus rare large-batch summaries beat the raw agent by 2.6 points at lower cost than either method alone. The only statistically significant drops were for the thinking variant, a reminder that every model needs its own evaluation.

Other studies agree. Keeping the last five observations scored 18.0% on SWE-bench Lite against 15.0% for full history in SWE-agent's ablations ([Yang et al., NeurIPS 2024](https://arxiv.org/abs/2405.15793)). AgentDiet's removal of useless, redundant and expired trajectory content cut input tokens **39.9–59.7%** at equal performance ([Xiao et al., FSE 2026](https://arxiv.org/abs/2509.23586)), and the 176-setting study found "staging rule-based elision before LLM-based summarization" the most efficient combination [2026 preprint] ([Fan et al.](https://arxiv.org/abs/2609.20804)). Anthropic ships the same idea as tool-result clearing, which triggers at 100K input tokens, keeps the three most recent tool pairs, and uses a `clear_at_least` floor so each cache-invalidating edit frees enough to be worth it ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)); it reports **+29%** from clearing alone and **84% fewer tokens** on a 100-turn search eval [vendor] ([Claude blog](https://claude.com/blog/context-management)). Compacting on every turn instead lowered success for most off-the-shelf models on TerminalBench-2 [2026 preprint] ([Hoy et al., arXiv 2609.35540](https://arxiv.org/abs/2609.35540)).

In Xylo the change belongs in `AgentLoop::fit` and `provider_guard.rs`, which today return early whenever history sits under the 80% trigger. A new masking pass should run once history passes about 50–60% of `W_eff` minus the output reserve, replacing tool results older than the last *K* completed tool rounds (start *K* between Anthropic's default of 3 and JetBrains' 10) with a one-line stub. The stub should name the tool, its key arguments and the original size, point to the existing `artifacts/tool-<id>.txt` spill or the journal entry, and state that the file is the authoritative copy and how to page it; in one preprint, naming the authoritative output recovered **6.3–7.9 points** for GPT-5.x models that otherwise answered from the wrong file [2026 preprint] ([Zhang et al., arXiv 2610.26836](https://arxiv.org/abs/2610.26836)). User messages, the assistant's tool calls and error results should never be masked, though repeated identical errors can collapse into one line with a count, following Manus's advice to keep failures visible ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). The mask should be persisted in the checkpoint the way the summary is, so later calls replay identical bytes, and the mask boundary should advance only in batches that free a meaningful share of the window, such as 20–30%; cache-aware batching of this kind cut input cost about 40% in one preprint [2026 preprint] ([Yao et al., arXiv 2609.37012](https://arxiv.org/abs/2609.37012)). A static per-tool retention table can keep edit diffs and test failures longer while masking directory listings, greps and web fetches sooner, since a learned per-tool policy beat a static one by only 15–18% [2026 preprint] ([Lin et al., arXiv 2608.29363](https://arxiv.org/abs/2608.29363)). The existing request-only shrink ladder and tool-notes fallback then become the emergency tier.

The cost case for masking is weaker and more contested than the quality case. The most aggressive tool-output compression in one study cut tool-output tokens 38.4% yet **raised billed cost 6.8%**, because cache writes and reads dominate input cost [2026 preprint] ([Weinberger & Hozez, arXiv 2607.12161](https://arxiv.org/abs/2607.12161)). Across 600 coding trajectories, **turn count explained 84% of cost variance and observation size only 4%** [2026 preprint] ([Kumar & Pandey, arXiv 2610.15093](https://arxiv.org/abs/2610.15093)), and the compaction threshold did not measurably affect results for two 1M-window frontier models [2026 preprint] ([Salle et al., arXiv 2610.31778](https://arxiv.org/abs/2610.31778)). On large-window cloud models, masking thresholds should therefore be set for cache economics; on small local windows, for fit and quality. Whether masked content must stay recoverable is also unsettled: DTOC found reversibility "critical" and non-restorable compression harmful ([Chaturvedi et al., Discovery Science 2026](https://arxiv.org/abs/2609.26121)), while the 176-setting study found models rarely used recoverability machinery [2026 preprint]. Xylo already spills full results to files, so keeping them recoverable costs almost nothing.

### Summaries lose constraints, paths and dates unless the harness pins them

Xylo's summarizer follows good practice in several ways. It keeps a verbatim tail and the current user request, never separates a tool call from its result, asks for five sections in under 900 words, and updates an existing summary rather than regenerating it (`prompts/compaction.md`, `compaction-update.md`). Updating is the right choice: Factory's evaluation scored anchored incremental summaries at 3.70/5 against 3.44 for Anthropic's regenerate-each-time SDK compaction and 3.35 for OpenAI's opaque endpoint [vendor] ([Factory](https://factory.com/news/evaluating-compression)), and ACE names the failure modes that regeneration causes, "brevity bias" and "context collapse" ([Zhang et al., ICLR 2026](https://arxiv.org/abs/2510.04618)).

Recent studies, mostly single-team preprints, agree on what LLM summaries reliably drop. Every compressor Factory tested scored only 2.19–2.45/5 on tracking files and artifacts [vendor]. Compact-Bench found LLM summaries kept at most **16.0%** of recurring details, against **79.1%** for mechanical extraction [2026 preprint] ([arXiv 2610.31710](https://arxiv.org/abs/2610.31710)). Salle et al. found the first compaction dropped about **a third of anti-cheating rules**, and that "how-to-work / don't-do" instructions were dropped about **6× more often** than specifications of what to build [2026 preprint] ([Salle et al.](https://arxiv.org/abs/2610.31778)). A one-sentence prompt change raised preservation of dates and times from **3.05% to 62.39%** [2026 preprint] ([arXiv 2608.11775](https://arxiv.org/abs/2608.11775)), and in 83% of failed compacted runs the failure traced back to a summary entry with no support in the environment, so deleting unsupported entries improved reliability by 2.1–8.9% [2026 preprint] ([Min & Chen, arXiv 2610.20927](https://arxiv.org/abs/2610.20927)).

Each finding maps onto a concrete change, under one principle: the harness, not the summarizer, should own anything it can derive deterministically. Xylo should build an artifact ledger from the action journal (files read, created and modified; commands run with exit codes; last test status) and append it verbatim beside the summary message. It should keep every earlier user message verbatim within a budget, not only the current "anchor" request, so user constraints never pass through the summarizer. `prompts/compaction.md` should require exact paths, identifiers, error strings and dates, and should ask the summarizer to cite a source tool-call id for each decision so an unsupported-entry filter has something to check. Summaries should also be allowed a separate, cheaper model, since today they always use the turn's own provider, and summarizing should start in the background once history passes about 60% so the result is ready when needed. This matters locally: Bud measured a median of **161 seconds per summary** on local hardware [2026 preprint] ([arXiv 2610.25516](https://arxiv.org/abs/2610.25516)), while Xylo's summarizer deadline is the smaller of the provider timeout and 90 seconds, so on slow local models summaries will often time out and fall through to the lossy excerpt fallback. Once an eval harness exists, the compaction prompt can be tuned on Xylo's own failures the way ACON did, by contrasting runs where full context succeeds and compressed context fails. ACON matched uncompressed AppWorld accuracy (56.5% against 56.0%) with peak context cut from 9.93K to 7.33K tokens, and its compressors distilled into small models kept over 95% of the teacher's performance ([Kang et al., ICML 2026](https://arxiv.org/abs/2510.00615)).

Two cheap additions complete the picture. The first is recitation: the harness should re-inject the current `todo_write` state and pinned constraints as a short note at the tail of the context. Manus credits rewriting its `todo.md` with keeping goals in recent attention across about 50 tool calls ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)), and Du et al. got up to **+4%** on RULER for GPT-4o by having the model recite evidence before answering ([Du et al.](https://arxiv.org/abs/2510.05381)). Xylo already has the delivery mechanism in the user-role `<application_note>` it appends for permission changes (`agent_loop/mod.rs`, `application_note`), and appending at the tail leaves the cache intact. The second is manual compaction and fresh restarts, neither of which exists today. Models drop an average of **39%** in multi-turn, underspecified conversations and "do not recover" from early wrong turns ([Laban et al., arXiv 2505.06120](https://arxiv.org/abs/2505.06120)), and Anthropic's own guidance suggests a fresh window can beat compaction for recent Claude models that rediscover state from files ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). A user-triggered `/compact` and a "restart from the summary and todo" action give users the escape hatch this evidence supports.

### Per-turn memory retrieval quietly breaks the prompt cache

Prompt caching is the largest cost and latency lever for agents, whose input dwarfs their output. One multi-provider study found caching cut API cost **41–80%** and time to first token **13–31%** across OpenAI, Anthropic and Google, with careful exclusion of dynamic content beating naive full-context caching [2026 preprint] ([Lumer et al., arXiv 2601.06007](https://arxiv.org/abs/2601.06007)). Manus reports about a **100:1 input-to-output ratio** and a 10× price gap between cached and uncached tokens on Claude Sonnet [vendor] ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)), and in public coding trajectories **98.6% of input tokens** came from the prefix cache [2026 preprint] ([arXiv 2610.15093](https://arxiv.org/abs/2610.15093)). Two agents on the same model differed in cost by **more than 20×, mostly through caching** [2026 preprint] ([Ariño de la Rubia & Pafka, arXiv 2609.33812](https://arxiv.org/abs/2609.33812)), and a linter found 32 caching mis-integrations across 571 projects, most of which "fail silently" ([CACHELINT, ICSE 2027](https://arxiv.org/abs/2610.34817)).

The mechanics are strict. Anthropic caches in the order tools, then system, then messages; a change at one level invalidates that level and everything after it, and changing tool definitions invalidates everything ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). OpenAI's guidance is to keep tool definitions and their order stable and to restrict tools with `allowed_tools` rather than removing them ([OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching)).

Xylo builds its system prompt once per turn, so it is byte-stable within a turn, but it breaks the cache across turns in four ways. First, fact titles from `recall_sync(workspace, prompt, 8)` and learned procedures from `relevant_skills(workspace, prompt, 2)` are retrieved with the current user prompt as the query and placed in the system block (`tools/mod.rs`, around `:248–287`), so a new turn with a different prompt can change that block and invalidate the cached prefix of the entire conversation. Second, read-only mode filters write tools out of the offered list (`usable` in `tools/mod.rs`) and schemas are re-read on every model call, so toggling permission mode mid-session rewrites the tools block, the most expensive miss there is. The filtering is redundant anyway, because the broker already refuses disallowed calls and appends an application note. Third, after compaction the summary becomes a second system block and takes over the system breakpoint, leaving the static prompt in front of it without its own breakpoint, even though Anthropic allows four and Xylo uses three. Fourth, Bedrock gets no `cachePoint`, OpenAI no `prompt_cache_key` and Gemini no `cachedContent`, and provider cache counters are displayed but never asserted on.

The fixes are small. Retrieved fact titles and learned-procedure lines should move out of the system prompt into a note attached to each new user message, where they become append-only history and stay cached. The stable parts (identity, environment with its day-granularity date, permission policy, project instructions and the built-in skills index) stay in the system block. Tools should be gated by permission rather than filtered, the fourth Anthropic breakpoint should go on the static system block, Bedrock should get a `cachePoint`, and OpenAI requests should carry a `prompt_cache_key` derived from the session id. `prompts/tests.rs` should assert that the system block is byte-identical across two turns with different prompts, and cache read and write tokens should flow into `ContextUsage` so regressions show up.

Local inference benefits even more. Reusing precomputed attention states cut time to first token **8× on GPU and 60× on CPU** ([Gim et al., MLSys 2024](https://arxiv.org/abs/2311.04934)). llama.cpp reuses the previous request's KV cache by default through `cache_prompt`, and its `--cache-reuse` option salvages later chunks when the middle of a prompt changes, which is exactly what Xylo's masking and summary edits do ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). Xylo already holds a single-slot lease for app-managed loopback servers (`provider_guard.rs`, around `:54–133`); pinning each session to one slot with prompt caching on, and keeping masking edits rare and batched, stops slow local prefill from repeating on every step.

## Tool calling: validate, rank and shrink before adding cleverness

### Ranked search should replace substring matching

Tool-calling accuracy falls along three separate axes. IBM's LongFuncEval measured drops of **7–85%** as the number of tools grew, **7–91%** in answer retrieval as tool responses lengthened, and **13–40%** as conversations got longer ([IBM Research, arXiv 2505.10570](https://arxiv.org/abs/2505.10570)). Deferred loading behind a search step is the best-supported fix. Anthropic's Tool Search Tool cut tool-definition tokens by **85%** (from about 77K to 8.7K) and raised MCP-eval accuracy for **Opus 4 from 49% to 74%** and for **Opus 4.5 from 79.5% to 88.1%** [vendor] ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)); Anthropic ships BM25 and regex variants, recommends keeping the 3–5 most-used tools always loaded, and suggests search once definitions pass 10K tokens or 10 tools.

Independent work points the same way. RAG-MCP roughly tripled tool-selection accuracy, from 13.62% to 43.13% ([Gan et al., arXiv 2505.03275](https://arxiv.org/abs/2505.03275)), while ToolRet found off-the-shelf retrievers mediocre at finding tools ([Shi et al., arXiv 2503.01763](https://arxiv.org/abs/2503.01763)) and Toolshed gained 46–56 points of absolute Recall@5 by enriching tool documents with synthetic questions and topics at index time ([Lumer et al., arXiv 2410.14594](https://arxiv.org/abs/2410.14594)). A preprint that instrumented Claude Code and Codex found filtering tool schemas "the only unambiguously and reproducibly positive lever" for multi-turn cost, removing 21K–57K tokens on a typical turn [2026 preprint] ([Chen & Shi, arXiv 2609.22114](https://arxiv.org/abs/2609.22114)).

Xylo has the deferral but not the retrieval. `search_tools` returns the first 12 tools whose name or description contains *any* query word as a substring, in registration order and without ranking (`tools/mod.rs`, around `:941–961`), so common words like "file" or "read" match many tools and ties favor whatever registered first. MCP tools are not in that index at all: the model must go from `connector_list` to `connector_tools` to `connector_call`, and `connector_tools` for stdio servers counts as a write, so it asks for approval in Ask mode. Calling a nonexistent tool returns a generic "Use search_tools" message.

The upgrade replaces substring matching with BM25 over name, description, parameter names and family or server name, using SQLite FTS5 (already used in the services crate) or an in-memory index. The local `bge-small` embedding asset and the reciprocal-rank fusion code in `services/memory.rs` can be reused as an optional second signal. When an MCP server connects, Xylo can generate synthetic queries per tool once and cache them by schema hash, in the Toolshed and Re-Invoke style ([Chen et al., arXiv 2408.01875](https://arxiv.org/abs/2408.01875)). MCP tools should join the same index under `server__tool` names, since Microsoft counted **775 tool-name collisions** across 1,470 servers ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale/)), so one search surfaces them while `connector_call` still does the dispatch. Unknown tool names should get the three closest names by edit distance or BM25. On non-Anthropic providers, Xylo should keep the `call_tool` indirection rather than promoting discovered schemas into the native tools array, because adding to that array rewrites the front of the cached prefix; Anthropic's native `defer_loading` beta is the cache-safe exception [vendor].

Third-party MCP descriptions should be treated as untrusted ranking input. Editing only a tool's description produced **more than 10× more usage** of that tool ([Faghih et al., arXiv 2505.18135](https://arxiv.org/abs/2505.18135)), and adversarially tuned names and descriptions raised selection from about 20% to as high as **81%** ([Sneh et al., arXiv 2510.02554](https://arxiv.org/abs/2510.02554)), so built-in tools should rank first where capabilities overlap. For small local windows, the resident core should also shrink: nineteen `CORE_TOOLS` plus configured families is too much for an 8K window, and a core of about eight tools (read, edit, search, shell, `todo_write`, `search_tools`, `call_tool`, `memory_search`) with the rest deferred fits Anthropic's 3–5-tool guidance in spirit. The trade-off is that deferral asks a weak model to run a two-hop search-then-call protocol, and Docker's tests show local models already struggle to pick the right tool and fill its arguments ([Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)). TinyAgent and "Less is More" have the harness choose relevant tools for the model instead ([Erdogan et al., arXiv 2409.00608](https://arxiv.org/abs/2409.00608); [Paramanayakam et al., arXiv 2411.15399](https://arxiv.org/abs/2411.15399)). For local sessions, the safest version picks a stable tool set once per session so the local KV cache survives, and measurement should decide whether per-turn selection is worth a prefill rebuild.

### Schema validation and a text protocol rescue local models

Small open models now call tools well on simple tasks, but they fail procedurally. Docker's evaluation of 21 models over 3,570 cases found Qwen3 14B at Q4 reaching **0.971 tool-selection F1** against GPT-4's 0.974, while Llama 3.3 70B scored 0.607 and quantization made no significant difference ([Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)). Its failure modes were eager invocation (calling tools on "Hi there!"), wrong tools, invalid or missing arguments and ignored tool output, at about **84–142 seconds per local interaction**. A 12-category error taxonomy found tool initialization and procedural errors are the main bottleneck for smaller models [2026 preprint] ([Huang et al., arXiv 2601.16280](https://arxiv.org/abs/2601.16280)). Guardrails pay off: SWE-agent's linter, which rejects syntactically broken edits, raised SWE-bench Lite from 15.0% to 18.0%, with cascading failed edits making up **23.4% of unresolved failures** ([Yang et al., NeurIPS 2024](https://arxiv.org/abs/2405.15793)), and adding usage examples to tool definitions raised complex-parameter accuracy from **72% to 90%** [vendor] ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)).

Xylo's dispatcher checks only that arguments parse as a JSON object (`dispatch::prepare`); `jsonschema` is not a dependency, each tool parses its own arguments, and there is no text-format tool-call parser, constrained decoding or JSON repair. OpenAI Responses functions go out with `strict:false`. A validation step belongs in `dispatch::prepare`, ahead of `permissions::decide`, so users never see an approval prompt for a call that would fail anyway. It should parse leniently (stripping code fences, trailing commas and single quotes, and taking the first balanced object), validate the result against the tool's effective schema, coerce safe types such as `"5"` to `5`, and on failure return a structured error with the failing path, the expected schema fragment and a correct example, allowing two or three retries per call signature. Per-model counts of invalid JSON, schema failures, unknown tools and eager calls should be logged. For OpenAI, `strict:true` is worth enabling wherever schemas allow it; OpenAI reported 100% schema adherence under strict mode against under 40% for an older model [vendor, unverified] ([OpenAI](https://openai.com/index/introducing-structured-outputs-in-the-api/)).

Local models also need a second wire format. Today Ollama, LM Studio, llama.cpp and vLLM all go through the Chat Completions adapter with native `tools`. A "prompted" mode would describe tools in the system prompt and parse Hermes or Qwen-style `<tool_call>{…}</tool_call>` blocks out of the streamed text (`providers/request.rs`, `stream.rs`). BFCL scores models in both native and prompted modes, which makes prompted calling a legitimate, measured path ([BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)). Xylo should choose the mode per model from a short built-in eval run when the model is added, covering simple, multiple, parallel and irrelevance cases plus Xylo's own tools, and store the result in the model's configuration. For the weakest models, Natural Language Tools splits *selection* (a plain-text yes or no per tool) from argument filling, and reported **+18.4 points** of tool-calling accuracy and **70% less output variance** across 10 models, with open-weight models gaining most ([Johnson et al., arXiv 2510.14453](https://arxiv.org/abs/2510.14453)). A 2026 replication reportedly confirmed the effect, and a secondhand write-up says Gemini 2.5 Pro lost accuracy [unverified], so NLT should be opt-in per model rather than a default.

Constraint should cover only the tool-call span, never the reasoning. Forcing answer-only schemas on small models raised schema validity from 61.5% to 100% but cut answer accuracy from **19.7% to 11.0%**, and Qwen2.5-1.5B's executable accuracy fell from **91.5% to 48.0%** [2026 preprint] ([Ray, arXiv 2605.26128](https://arxiv.org/abs/2605.26128)). Writing a free-form draft and then decoding under constraints recovered up to **+24 points** [2026 preprint] ([Reddy et al., arXiv 2603.03305](https://arxiv.org/abs/2603.03305)), and the broader debate over format restrictions remains open ([Tam et al., arXiv 2408.02442](https://arxiv.org/abs/2408.02442); [.txt rebuttal](https://blog.dottxt.co/say-what-you-mean.html)). Per llama.cpp's documentation, which the notes did not re-check, its `--jinja` function calling uses "lazy" grammars that switch on only once a tool call begins, which is the right shape for Xylo's local path [unverified] ([llama.cpp docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). Docker's eager-invocation finding also argues for an explicit "answer directly when no tool is needed" instruction and for irrelevance cases in the per-model eval.

### SWE-agent-style interfaces keep observations small and actionable

Interface design moves scores. SWE-agent's ablations on SWE-bench Lite ([Yang et al., NeurIPS 2024](https://arxiv.org/abs/2405.15793)) show the size of the effect:

| Interface choice | SWE-bench Lite |
|---|---|
| 100-line file viewer | **18.0%** |
| 30-line viewer | 14.3% |
| Full file | **12.7%** |
| Summarized search, capped at 50 results with a "be more specific" refusal | **18.0%** |
| Iterative search | **12.0%** |

Xylo's `file_read` defaults to 2,000 lines and 40 KiB (`code.rs`), far from the evidence-backed window and more than small local windows can absorb. Its default should scale from `W_eff`, starting around 100–300 lines while keeping `next_offset` paging, and `search_project` should return a per-file summary first with a hard result cap. A fast syntax check when an edit is previewed, while the `EditLock` is held, is the Rust equivalent of SWE-agent's linter guardrail: a tree-sitter parse that rejects any edit introducing parse errors.

Tool errors also go unflagged more often than not. Microsoft found GPT-4.1 judged about **59% of unflagged MCP results** to actually contain errors ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale/)). Xylo already wraps results that report failure as "Tool reported an unsuccessful result" (`observation_failed` in `tools/mod.rs`), and that heuristic should extend to MCP text showing HTTP 4xx or 5xx codes, "unauthorized", "not found", or empty results where data was expected. One concurrency fix is free: dispatch classifies access from each tool's static `writes` flag (`access` in `broker_tools.rs`), and `connector_call` is statically a write, so every MCP call runs serially even when its `readOnlyHint` annotation already makes it read-only for permission purposes. Scheduling should use the annotation-based classification too, and when a batch holds several calls that need approval, one prompt should list them all. No source measured that last change, but it follows from the approval-fatigue evidence in the security discussion below.

### Code mode is a later, cloud-only bet

Letting the model write code that calls tools reduces round-trips. CodeAct reported **up to 20% higher success** than JSON or text actions across 17 models ([Wang et al., ICML 2024](https://arxiv.org/abs/2402.01030)). Anthropic reports one MCP workflow falling from **150K to 2K tokens** [vendor] ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)) and its Programmatic Tool Calling averaging **37% fewer tokens** with modest accuracy gains (25.6% to 28.5% on internal knowledge retrieval) [vendor] ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)), while Cloudflare's Code Mode post gives no benchmarks at all [vendor] ([Cloudflare](https://blog.cloudflare.com/code-mode/)). The notes found no evidence that models of 14B or smaller benefit. Because turn count dominates cloud cost (84% of variance in the TurnCost study [2026 preprint]), code mode is a real cloud lever, but it is a larger project: a `run_code` tool over generated stubs whose inner calls route back through `execute_scoped`, so approvals, the journal and secret handling apply to each inner call. It belongs after the quick wins and only for strong cloud models.

## Agent loop: recovery, not planning, is the weakest link

### Three silent failure paths and no stall detector

METR attributes the steady growth in how long agents can work mainly to "greater reliability and ability to adapt to mistakes" ([Kwa et al., NeurIPS 2025](https://arxiv.org/abs/2503.14499)). Meta's production data puts misbehavior (specification drift, reasoning loops and tool-call failures) at about **30% of coding-agent trajectories**, and a lightweight observer that injects targeted guidance resolved **90% of misbehaviors needing a single intervention** [2026 preprint] ([Nanda et al., arXiv 2602.17037](https://arxiv.org/abs/2602.17037)).

Xylo's loop has four confirmed gaps here. It never reads `ModelResponse.finish`, so a `Length` cutoff with no tool calls is returned as the final answer. An empty response with no tool calls ends the turn as-is. A context overflow fails the turn, as covered above. And nothing detects repeated calls or stalls beyond the 400-call `MAX_MODEL_CALLS` cap. The first gap is worse than it looks, because the desktop caps output at a quarter of the context (2K tokens on an 8K window), so long edits and answers get cut off routinely; one harness study traced part of a harness's deficit to output caps cutting runs short [2026 preprint] ([Liu & Han](https://arxiv.org/abs/2610.04433)).

The fixes sit in `steps()`. In the no-tool-call branch, the loop should read `finish`: a `Length` cutoff without tool calls keeps the partial message and asks the model to continue, up to two or three times; a `Length` cutoff that truncated a tool call returns an error result asking for a smaller or chunked call; and an empty response gets one retry with a nudge before an error surfaces. After each `run_batch`, a deterministic loop detector should hash each tool name with its canonical arguments, and each call with its result, and fire on three or four identical consecutive pairs, on A-B-A-B cycles, on the same call signature failing three times, or on K steps with no file change and no todo update. OpenHands enables such a detector by default at four identical action-observation pairs ([OpenHands docs](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)). The response should escalate from a visible harness note ("you have run X four times with the same result; change approach or ask the user") to a pause for user input, with termination as the last resort, and soft warnings should fire at 80% of the step and wall-clock budgets. Xylo's module doc promises "no hidden prompting," so these notes should travel through the existing `application_note` and steering path and appear in the UI labeled as harness-originated. An asynchronous monitor model in the style of Meta's observer is a later step: a small parallel "companion" cut repetition **52–62% at about 11% overhead** but did not help 1–1.5B models [2026 preprint] ([Khan & Khan, arXiv 2604.13759](https://arxiv.org/abs/2604.13759)).

### Verification belongs in the tool layer

Intrinsic self-correction without external feedback does not reliably help and sometimes hurts ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)). Even with execution available, terminal agents caught only **61.43%** of their own wrong solutions and repaired **49.36%** of those [2026 preprint] ([Luo et al., arXiv 2609.38812](https://arxiv.org/abs/2609.38812)). What works is verification grounded in execution. Agentless reached 32% on SWE-bench Lite at $0.70 per issue by selecting patches with reproduction and regression tests ([Xia et al., arXiv 2407.01489](https://arxiv.org/abs/2407.01489)), and Large Language Monkeys showed coverage rising from **15.9% to 56%** between one and 250 samples, while majority voting plateaued without a verifier ([Brown et al., arXiv 2407.21787](https://arxiv.org/abs/2407.21787)). Anthropic's long-running harness found that requiring end-to-end browser testing "substantially improved" results over unit tests or curl checks, though it reported no benchmark numbers [vendor] ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

Xylo has no planner beyond `todo_write` and no verification gate, and three changes follow from the evidence. The first is the tree-sitter check on edit described above. The second is a verify-before-done note: when a turn has modified files and no build or test command has run since the last edit, the no-tool-call branch adds one visible note asking the model to run the project's test command or explain why not, filling in the build and test commands that Xylo's learned procedures already capture. The third is an optional verifier subagent that receives a fresh context, the diff and the acceptance criteria, but not the worker's reasoning. For local models, Xylo could also offer N attempts in isolated git worktrees with selection by tests: when a small model has non-trivial success on a problem, test-time compute can beat a model 14× larger at matched FLOPs ([Snell et al., arXiv 2408.03314](https://arxiv.org/abs/2408.03314)). Root-cause feedback that points at the first faulty step, instead of a generic "try again," gave up to **26% relative** task-success gains ([Zhu et al., arXiv 2509.25370](https://arxiv.org/abs/2509.25370)).

### Subagents pay off only with narrow contracts

Multi-agent evidence splits by task shape. Anthropic's Opus-led research system beat a single agent by **90.2% at about 15× the tokens of chat** on breadth-first research, and Anthropic itself calls most coding tasks a poor fit [vendor] ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Across 260 controlled configurations, multi-agent setups ranged from **+80.8%** on decomposable tasks to **−70.0%** on sequential planning, and architectures without centralized verification propagated errors ([Kim et al., arXiv 2512.08296](https://arxiv.org/abs/2512.08296)). In coding harnesses, task-specific subagents gave stable gains while general-purpose subagents could hurt repository generation [2026 preprint] ([Hu et al.](https://arxiv.org/abs/2609.32459)), and running a skill as a subagent with a fresh context beat loading it in context on long horizons, but only when the skill had a clear input/output contract [2026 preprint] ([Piriyakulkij et al., arXiv 2609.09233](https://arxiv.org/abs/2609.09233)). Recursive child threads gained **10–50 points** with Llama-3-8B and CodeLlama-7B ([Schroeder et al., arXiv 2405.17402](https://arxiv.org/abs/2405.17402)), and Cognition argues that parallel writers make conflicting implicit decisions ([Cognition](https://cognition.com/blog/dont-build-multi-agents)).

Xylo's `agent_delegate` is one generic helper. It runs on the parent's model at depth 1 with two slots, returns up to 64 KB of final text, repeats its task text in both the system `# Task` section and the user message, has no budget beyond 400 calls and 15 minutes, is neither streamed nor steerable, and discards its transcript. It should become a set of contract-bound roles (`subagent.rs`, `prompts/subagent.md`): an explore role with read-only tools that returns a report of about 1.5K tokens plus file paths (Anthropic says subagents typically return 1–2K tokens ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))), the verify role above, and the forked skills that already exist. Each role should declare an objective, an output format, a tool allowlist and a token and step budget, with bulky output written to artifact files and writes kept in the main agent. Allowing a different model per role keeps the main agent's cache warm while cheaper or local models handle exploration and summaries. Switching from an expensive model to a cheaper one recovered its cache cost within two calls in one study, while switching upward never broke even [2026 preprint] ([Parashar et al., arXiv 2610.19292](https://arxiv.org/abs/2610.19292)); another found delegating turns to cheaper models raised cost in half of settings [2026 preprint] ([arXiv 2610.15093](https://arxiv.org/abs/2610.15093)), so delegation should be measured before it becomes a default. The duplicated task text should go, child transcripts should be persisted for later search and debugging, and steering and cancellation should reach running children.

### Untrusted tool output needs architectural defenses

Prompt-level defenses do not hold. Adaptive attacks bypassed **12 published defenses at over 90% attack success** ([Nasr et al., arXiv 2510.09023](https://arxiv.org/abs/2510.09023)). MCP tool poisoning reached **72.8%** attack success on o1-mini, more capable models were often *more* susceptible, and the best refusal rate was under 3% ([Wang et al., arXiv 2508.14925](https://arxiv.org/abs/2508.14925)). For 2–14B open models, changing only the system prompt moved InjecAgent attack success from **0.2% to 43%**, and most failed attacks were ignored rather than refused [2026 preprint] ([Zarif et al., arXiv 2610.23254](https://arxiv.org/abs/2610.23254)). Architectural controls do hold: CaMeL kept **77%** task success, against 84% undefended, with provable security ([Debenedetti et al., arXiv 2503.18813](https://arxiv.org/abs/2503.18813)), and OS sandboxing cut permission prompts **84%** in Anthropic's internal use [vendor] ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)).

Xylo already has deterministic permission modes, risk tables over parsed shell words, justified network requests and MCP annotations. The architecture notes do not record tool-definition pinning or session taint tracking, so their absence should be confirmed before building them. The cheapest model-agnostic additions are Rule-of-Two session flags in the broker, which track untrusted input seen (web, browser or MCP output), sensitive access and external side effects, and require approval whenever all three would meet ([Willison's summary of Meta's Rule of Two](https://simonw.substack.com/p/new-prompt-injection-papers-agents)), plus rug-pull protection that hashes each connector's tool list and descriptions at approval and shows a diff when they change ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)). These matter most for local models, whose apparent robustness swings with prompt wording.

## Memory: provenance and supersession matter more than embeddings

### Lexical search and searchable transcripts are strong baselines

Simple retrieval holds up well against elaborate memory systems. On MemoryAgentBench's accurate-retrieval task, BM25 scored **60.5**, ahead of embedding retrievers at 53.8–54.7 and far ahead of structured memory systems (Zep 37.5, MemGPT 34.3, Mem0 32.6), while selective forgetting with multi-hop conflicts topped out at **28%** for every method ([Hu et al., arXiv 2507.05257](https://arxiv.org/html/2507.05257v4)). Mem0's own paper found its full-context baseline at **72.90** on LoCoMo, ahead of Mem0's 66.88 [vendor] ([Chhikara et al., arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). Agents that search plain files do well: a GPT-4o-mini agent grepping files scored **74.0%** on LoCoMo [vendor] ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)), and on LongMemEval-V2, storing past trajectories as files and letting a coding agent gather evidence scored **72.5%** against 48.5% for the best RAG baseline, at high latency [2026 preprint] ([Wu et al., arXiv 2605.12493](https://arxiv.org/abs/2605.12493)). The original LongMemEval supplies two further lessons. Indexing each item under its extracted facts as well as its raw text added **9.4% recall and 5.4% accuracy**, and Llama 3.1 8B's accuracy **dropped sharply beyond about 3K retrieved tokens** while GPT-4o kept improving past 20K; time-aware query expansion did not help the 8B model ([Wu et al., ICLR 2025](https://arxiv.org/html/2410.10813v2)).

Xylo's fact store already matches the production consensus, fusing FTS5 BM25 with optional local embeddings by reciprocal-rank fusion and falling back to lexical search alone. The gaps lie around it. Search over past conversations exists (`services/history_search.rs`) but only the UI can use it, fact titles are injected into the system prompt each turn (which also busts the cache, as covered above), and nothing indexes past tool outputs or transcripts for retrieval. Three changes follow. Project-scoped `history_search` and `history_read` tools over the existing `messages` FTS index and the action journal would let the agent recover "how did we do X last time" and see old tool outputs, the design with the strongest support for coding agents on capable models; Cursor applies the same idea by keeping chat history searchable after summarization [vendor] ([Cursor](https://cursor.com/blog/dynamic-context-discovery)). Small local models, which write weak search queries and degrade with too much retrieved text, should instead get the top 3–5 items injected automatically under a cap of about 1–2K tokens. And facts should be indexed under their entities, with extra FTS rows for file paths, symbols and package names extracted by regex or tree-sitter, so a query mentioning `provider_guard.rs` finds facts about it. Embeddings should stay an optional signal in the hybrid rather than its backbone: an independent replication attributed MemPalace's viral **96.6% Recall@5** to verbatim storage plus a small default embedding model, not to its architecture [2026 preprint] ([Dey & Viradecha, arXiv 2604.21284](https://arxiv.org/abs/2604.21284)).

### Writes must be non-destructive and origin-bound

Systems that let an LLM rewrite memory lose information. Mem0 reversed its own design in 2026, dropping LLM-driven UPDATE and DELETE because that was "where context got destroyed" and now inserting only, with old and new versions side by side; it reports LongMemEval rising from **67.8 to 94.4** without naming its answer or judge models [vendor] ([Mem0](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)). Zep marks contradicted facts invalid with timestamps instead of deleting them [vendor] ([Rasmussen et al., arXiv 2501.13956](https://arxiv.org/abs/2501.13956)). HaluMem found memory systems accumulate hallucinations during extraction and updating, and those errors propagate into answers ([Chen et al., arXiv 2511.03506](https://arxiv.org/abs/2511.03506)). Ground Truth First found poorly written facts failed **24%** of the time against 2% for well-written ones, and that a capped, curated memory's recall of evicted content fell from 96% to **72%** over nine weeks [2026 preprint] ([Spencer, arXiv 2607.21962](https://arxiv.org/abs/2607.21962)).

Xylo's `memory_remember` always creates a new record with `supersedes: None` (`builtin.rs`, around `:499–509`), and corrections are possible only in the host UI. It should accept an optional `supersedes` id taken from `memory_search` results, plus a reason, and mark the old fact invalid with a timestamp rather than deleting it, so recall shows "previously: X (until date)." A write-quality gate should require facts to be self-contained, with no dangling pronouns, and to name their subject, while the harness stamps the date and attribution and near-duplicates increment a counter instead of inserting a new row.

Memory is also the most persistent attack surface. MINJA reached over 95% injection success through ordinary queries under idealized conditions, though a 2026 re-evaluation found existing legitimate memories blunt it ([Dong et al., arXiv 2503.03704](https://arxiv.org/abs/2503.03704); [arXiv 2601.05504](https://arxiv.org/abs/2601.05504)), and AgentPoison exceeded 80% attack success with under 0.1% of entries poisoned ([Chen et al., NeurIPS 2024](https://arxiv.org/abs/2407.12784)). Write-time provenance is the only defense with strong results, though both supporting papers are single-team and unreplicated. HMAC-signed provenance cut unsigned injection from **93–100% to 0%** [2026 preprint] ([arXiv 2606.12703](https://arxiv.org/abs/2606.12703)), and origin-bound authority reached 0% attack success across eight frontier models while showing that content-based defenses can be laundered through the agent's own summarization [2026 preprint] ([arXiv 2606.24322](https://arxiv.org/abs/2606.24322)). In Xylo the risk is concrete. In Ask mode `memory_remember` is auto-allowed (`permissions.rs`, around `:322–323`), and recalled fact titles are injected into the **system prompt** on later turns, so text from a web page or MCP output can lead the agent to write a fact that reappears with system-level placement in every later session of the project. The fix is an immutable `origin` set by the harness rather than the model's free-text `source` (user-typed, user-approved, agent-inferred, tool output or web content), with derived facts inheriting their least-trusted source. Facts that did not originate with the user should be injected as quoted, dated data in the tail note, never as instructions, memory writes should require approval once a session has read untrusted content, and secrets should be redacted before any write.

### Procedural memory should stay small, scored and reviewed

Distilling past work into reusable procedures helps under the right conditions. ReasoningBank, which stores short strategy items from both successes and failures and retrieves only the top one, lifted WebArena success from **40.5% to 48.8%** and SWE-bench Verified from 34.2% to 38.8% on Gemini 2.5 Flash ([Ouyang et al., ICLR 2026](https://arxiv.org/html/2509.25140v2)). ACE's itemized, incremental playbooks gained **10.6%** on agent tasks ([Zhang et al., ICLR 2026](https://arxiv.org/abs/2510.04618)), and curated skills raised average pass rates from **33.9% to 50.5%**, with focused skills beating large bundles [2026 preprint] ([Li et al., arXiv 2602.12670](https://arxiv.org/abs/2602.12670)). The 2026 counter-evidence is just as clear: agents "rarely form robust reusable skills," and **reusing raw trajectories often beats distilled skills** [2026 preprint] ([Lei et al., arXiv 2605.24117](https://arxiv.org/abs/2605.24117)), while skill retrieval precision fell from **29.6% to 3.3%** as the pool grew from 5 to 100 [2026 preprint] ([Jiang et al., arXiv 2608.14036](https://arxiv.org/abs/2608.14036)).

Xylo's learned procedures already respect these cautions: they are deterministic, promoted only after independent later evidence, suspended on counter-evidence and capped at two per turn. Four additions would strengthen them. Pitfall entries keyed by error signature would surface a lesson when a known failure recurs, as ReasoningBank and Reflexion do. Helpful and harmful counters, with deprecation for entries that later fail, follow ExpeL, ACE and Memp. Raw trajectories stay retrievable through the history tools above. And the background learning job Xylo already enqueues after each turn (`engine.rs`, around `:45–60`) can grow an idle-time consolidation step in which a stronger cloud model, when the user permits, drafts candidate facts and procedures from completed sessions into the existing `skill_propose` review queue. Sleep-time compute cut test-time compute about **5×** at equal accuracy ([Lin et al., arXiv 2504.13171](https://arxiv.org/abs/2504.13171)), LightMem's offline consolidation cut online token cost by up to **117×** ([Fang et al., ICLR 2026](https://arxiv.org/abs/2510.18866)), and procedures authored by stronger models transfer to weaker ones ([Fang et al., ACL 2026 Findings](https://arxiv.org/abs/2508.06433)). The division of labor is that cloud models author and local models consume.

## Prioritized roadmap: fix silent failures first, then build the eval harness

### Local and cloud models need different first moves

For **small local models**, the binding constraints are window size, procedural tool-call errors and slow prefill. What matters most is sizing everything from the effective window (including detecting the context the local server actually serves), early and batched masking with early summary triggers, recovery from context overflow, schema validation with repair, a prompted tool-call protocol for models without reliable native calling, a smaller resident tool set, small automatically injected memory, and architectural rather than prompt-level security. Fresh-context subagents and plan-then-execute modes help too, because they cut the number of long-context calls: LLMCompiler reported up to **3.7× lower latency** than ReAct ([Kim et al., ICML 2024](https://arxiv.org/abs/2312.04511)), and execution-guided plan repair lifted 1.5–4B planners from about 3% to 17–24% execution success on live MCP servers [2026 preprint] ([Bhandari et al., arXiv 2606.12674](https://arxiv.org/abs/2606.12674)). Local models also gain the most from cache stability, since llama.cpp prefill on consumer hardware is slow.

For **cloud frontier models**, the binding constraints are cost and long-horizon reliability. What matters most is prompt-cache stability with explicit cache keys, ranked tool search for MCP-heavy setups, agent-searchable history, contract-bound subagents on cheaper per-role models, verification gates and finish-reason recovery, followed later by code mode and requests for extended thinking. Anthropic and Gemini thinking is never requested today, and it should be exposed per phase rather than set to maximum, since higher reasoning effort reduced accuracy in most of HAL's runs ([Kapoor et al., arXiv 2510.11977](https://arxiv.org/abs/2510.11977)). Both populations need the eval harness, because per-model behavior diverges: NLT helps some models and reportedly hurts others, evidence substitution hit GPT-5.x but not Claude 4.6, and masking hurt only the thinking variant.

The tables rank changes by impact, evidence strength and effort. **Strong** evidence means several independent or peer-reviewed results agree; **Moderate** means one peer-reviewed study or consistent independent industry reports; **Emerging** means single-team 2026 preprints, vendor-only numbers or engineering inference. Expected impact quotes the closest published effect, and none of it has been measured on Xylo.

## Conclusion

Across all four areas, information gets lost wherever an LLM owns state the harness could own deterministically. Summaries drop paths, dates and prohibitions; LLM-driven memory updates erased facts badly enough that Mem0 reversed its own design; self-distilled skills underperform raw trajectories; and unsupported summary entries drive most failures in compacted runs. Xylo's engine already leans the other way, with a journal of record, deterministic procedure learning, harness-built checkpoints and a "no hidden prompting" rule. The highest-leverage strategy is to extend that stance, so the harness owns the artifact ledger, the pinned constraints, the mask boundary, the memory origin, the loop detector and the effective window, while LLMs handle only the judgment calls that cannot be derived deterministically.

The second takeaway is that "fewer tokens" stopped being a safe proxy for "better" or even "cheaper" in 2026. Compression raised billed cost when it broke caches, masking hurt a thinking model, retrieval through file pointers hurt some GPT-5.x versions but not Claude 4.6, and constrained decoding guaranteed valid output while halving small-model accuracy. The right abstraction for Xylo is therefore a per-model profile in `ProviderConfig`, chosen by Xylo's own evals and recording the effective window, the tool-call protocol, the output and reasoning reserve, the masking window and summarizer model, the memory injection cap and the cache strategy. Today's flat `context_tokens` and `output_tokens` pair cannot express these differences; a profile turns the literature's model-dependent findings into settings Xylo can measure and tune, instead of defaults that suit one model and fail the next.
