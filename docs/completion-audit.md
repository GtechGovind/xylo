# Product completion audit

The full native product plan remains the delivery scope. Development previews and passing fixtures are intermediate evidence. Colibri integration is deferred at the user's request; existing managed llama.cpp and external local-provider paths remain in scope.

The application uses current resource availability and task demand. It has no user-selected RAM profiles. All required capabilities belong in the standard product; heavy services start when used. Explicit model choice and explicit account authorization remain user decisions.

## Evidence rules

- Record the exact source state, binary hashes, dependency lock, hardware and configuration for a test run. A later source change requires the affected checks to run again.
- Separate source completion, deterministic fixtures, real service/device acceptance and release acceptance. Do not turn a fixture into a claim of production readiness.
- Measure release application overhead using a scripted provider. Report model/network quality, time and cost separately. Include child processes, browser, model weights and KV cache in active-memory reports.
- Treat 8/16/32 GB as test machines, never manual product modes. Preserve bounded queues/caches and system headroom while using available capacity automatically.
- Keep UI language about user tasks and results. This document and developer diagnostics carry implementation details.

The full product has **not** passed release acceptance. See [verification](verification.md) for targets and [performance measurements](performance.md) for reproducible commands and report limitations.
