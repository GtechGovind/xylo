# Saved conversation search and message navigation

Saved conversation search reads the database's title and message FTS5 index. It does not depend on the sidebar's currently loaded conversation page or the chat's loaded messages. A result includes a bounded snippet, conversation metadata and the actual source message UUID. Title-only matches have no message UUID and open the latest conversation view.

`Store::index_history_chunk(limit)` initializes an optional derived index and backfills at most 500 records and approximately 4 MiB per transaction. A single oversized message can exceed that byte target. The host runs these chunks off the UI thread, yielding between chunks. Insert, update and delete triggers maintain the index atomically with subsequent history writes, including writes during backfill. Timestamp-only conversation updates do not reindex unchanged titles. Search reports `indexing` until the initial snapshot is complete, and the UI reruns an active search after the ready event. Derived tables do not alter the application's schema version or eagerly load history at startup.

`Store::search_history(query, before, limit)` accepts at most 512 UTF-8 bytes. Up to eight Unicode alphanumeric terms become escaped prefix terms joined by AND; query text cannot introduce FTS operators. Results prefer the latest matching message within each conversation, with a title match as fallback. Pagination uses descending `(updated_at, id)` keys and returns at most 200 results with a next cursor and `has_more`. Snippets contain at most 24 FTS tokens and 320 Unicode characters. Full message JSON is not returned with search results. Updates between pages can move a conversation in recency order; this is a live view, not a frozen archive snapshot.

`Store::history_window(session, message_id, limit)` validates that the source belongs to the requested conversation and returns a centered chronological page of at most 200 messages. `history_after(session, after, limit)` returns the next append-order page. `HistoryWindow` exposes older/newer flags and append-row cursors independent of message timestamp ties. A newer response echoes its requested cursor in `request_after` for UI correlation. The application currently performs no VACUUM that can renumber implicit rowids; any future such maintenance must rebuild this derived index and invalidate active rowid cursors.

The native UI debounces input by 220 ms and correlates each result with request ID, exact query and current workspace. It displays a single virtualized 100-result page and offers First/Next navigation, keeping result memory bounded. Selecting a message hit opens and highlights that exact source in a centered native chat list, pauses tail following and keeps older/later navigation available. Later pages append while the active window fits within 400 messages; further paging replaces it with a bounded window whose earlier rows remain reachable through older navigation. Latest messages exits the historical window. Unsolicited latest-history refreshes cannot overwrite an active message jump. Wrong source anchors, newer-page cursors and workspace/session responses are rejected; loading has a bounded retry timeout.

Backend tests cover lazy/reopened indexing, concurrent insert/update/delete and title changes, exact source IDs, timestamp ties, deduplicated conversation paging, escaped FTS terms, centered windows and cross-session anchor rejection. The native interaction fixture uses a real Store and Host with 800 equal-timestamp messages. It searches a body-only hit outside loaded history, clicks the native result, verifies the exact source control is visible, loads later/earlier windows, retains the source during an unsolicited latest refresh, rejects stale anchor/cursor responses and returns to latest history. This establishes local deterministic behavior, not large-archive latency percentiles or acceptance on every desktop platform.
