# Project files and search

The native interface retains one folder page (at most 500 entries) and one search-result page (at most 100 matching lines). Folder navigation, First page and Next page keep the complete discovered project reachable. Search continuations advance by file and byte position; changing the query, case sensitivity or regular-expression setting cancels and invalidates the previous continuation. There is no 2,000-match ceiling.

The application host maintains a rebuildable SQLite catalogue under its private `workspace-index` directory. This catalogue is separate from the durable conversation database. Native paths use lossless platform byte keys; display text does not determine file identity. A background scan writes batches of at most 512 entries, publishes bounded progress and retains at most 256 changed/removed paths per notification. An incomplete change list tells the editor to conservatively recheck its current file.

The project root is listed before discovery of its descendants. Every traversal is shallow (`max_depth(1)`); the indexed SQLite directory frontier replaces an in-memory recursive stack and remains usable across a stopped scan. Opening a folder can seed its immediate children while the rest of the project is still being discovered. Directory pages use indexed keyset queries. Search loads at most 128 catalogue keys at a time and searches current file contents using the ripgrep libraries. A deadline can return a continuation even when no matches were found yet. Results produced during discovery are explicitly marked provisional.

Native filesystem events update the affected paths or subtrees. Ignore-file changes and bounded-event overflow request a streamed repair. Healthy native watching does not trigger a periodic full-project scan. If watching is unavailable, the interface shows a refresh notice and background repair backs off. Explicit Refresh files remains available. The catalogue and its own writes are excluded from project observation.

Blocking traversal, database queries and content reads run outside the GPUI event loop. Two concurrent catalogue queries are admitted per selected project, with permits retained until their actual blocking work finishes. Selecting another project cancels the old scan and requests; late responses cannot replace the new folder or editor selection. Navigating folders preserves unsaved editor contents.

New search reads use directory-handle authority and refuse substituted symlink/reparse ancestors. This does not qualify all existing editor read/save paths: their canonical-path authorization and parent-path replacement behavior still need equivalent authority and cross-platform race qualification. The initial Windows search-reader implementation supports local disk roots; UNC/network-root support and actual Windows filesystem behavior remain open acceptance items.

Native fixtures exercise complete paging of 1,201 root entries, navigation with unsaved edits, stale responses, 2,105 search matches and query/option changes. Backend fixtures separately cover indexed range queries, ignore rules, native path identity, watcher updates and anchored search reads. These are deterministic functional checks. They do not establish large-project latency, whole-application RAM, sustained frame pacing, physical input/accessibility behavior or Windows/Linux release acceptance. Current gate counts and source identities belong in [build-validation.json](build-validation.json).

Backend bounds, ignore-policy limitations and focused fixture scope are detailed in [native-workspace-index.md](native-workspace-index.md). External common/global Git ignore changes require explicit Refresh. Existing pinned ignore limitations for relative gitfile targets or missing `commondir` are retained rather than introducing a separate Git configuration policy.
