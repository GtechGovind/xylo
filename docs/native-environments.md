# Native execution environments

Saved environments use explicit native OpenSSH, Docker or Podman executables. The application stores their profiles and operation receipts under its configured private `native-management/environments` directory. It never downloads a client, image, credential or runtime, and profile creation does not launch a client. PATH discovery checks executable files only.

SSH setup requires a host, account, port and a known-hosts file whose keys the user has verified through their normal trust process. Authentication uses an existing SSH agent or an explicitly selected private identity file. The application neither reads private-key contents nor stores passwords. Connections use `BatchMode=yes`, `StrictHostKeyChecking=yes`, the selected known-hosts file, no automatic key updates, and no user/system SSH configuration or forwarding. Unknown or changed host keys fail. This is not an automatic trust-on-first-use workflow. [OpenSSH configuration reference](https://man.openbsd.org/ssh_config)

On Unix, Connect starts a supervised foreground OpenSSH multiplex master and verifies it with `ssh -O check`. A private short socket path avoids macOS Unix-domain path limits. Other application processes use that same socket after checking the stored profile; they do not need to own the master process. Command execution disables independent connection fallback if the checked master disappears. Disconnect requests master exit and stops the process owned by that service. Normal helper shutdown stops its owned masters; shutting down an agent worker does not close a helper-owned master. A restart may require Connect again: a stored `connected` flag alone never proves reachability. On other platforms, the native SSH client instead verifies an independent noninteractive command session; it does not claim to provide a persistent multiplex master. The remote account needs a POSIX-compatible command shell and `true` for this probe.

Existing containers are execution targets only. Connect inspects and pins the complete immutable container ID and requires a running container. Disconnect changes the application selection; it does not stop or remove the existing container. Managed containers use an explicitly selected, already local image and explicit startup argv. Create passes `--pull=never`, a deterministic application name and installation/profile/create-operation ownership labels. Start, Stop and Remove container inspect the immutable ID and labels again before dispatch. Removing a container requires it to be stopped; there is no force removal or volume deletion. Removing its profile first is refused. Images, mounts, ports, daemon configuration and privileged flags are not implicit profile settings. [Docker create reference](https://docs.docker.com/reference/cli/docker/container/create/), [Podman create reference](https://docs.podman.io/en/latest/markdown/podman-create.1.html)

## Revision and outcome handling

Every mutation and command requires a UUID operation identity and the current profile revision. A per-profile cross-process lease holds the selected target/executable identity stable through native execution. A short separate metadata lease protects atomic profile/receipt file replacement. Native argv contains no local shell; remote SSH argv is single-quoted at its explicit POSIX shell boundary. Commands cannot override the stored executable, host, container or working directory. Container execution uses the image's configured working directory; SSH commands start in the account's normal command-session directory. A command such as `cd` does not establish persistent shell state for later commands.

An operation is recorded and synced before native dispatch. Repeating the same identity with identical arguments returns the durable receipt; reusing it with different arguments is refused. Cancellation and timeout terminate the local client process tree. They do not prove that a server-side command or container effect did not happen. Interrupted commands become `outcome_unknown` and are never replayed automatically. A later lifecycle check can prove the requested container/connection state without repeating the mutation. Otherwise the user must inspect the actual target and explicitly record an observed outcome with a note before another command can run. CLI transport exit codes 125/255 are treated conservatively as uncertain. Other nonzero command exits retain their output and completed failure status; this does not assert rollback of any partial command effects.

Atomic profile changes carry the last operation ID, so a crash after updating the profile but before delivering its receipt can be recovered. Removing a profile retains a revision tombstone. Listing includes unresolved operation identities, allowing recovery after the UI or application loses a response. A missing receipt alone never proves that a request was not dispatched. A status request may additionally supply the original environment ID and action. The backend then takes the same per-operation lease used before all request validation/admission. A live admission returns Prepared. A quiescent missing operation receives a durable Cancelled fence before acknowledgement; a late original request with that identity must return Cancelled rather than execute. Wrong environment/action context is rejected. Missing context retains uncertainty.

Storage is bounded to 128 active profiles, 512 profile records including tombstones, 1,024 active receipts and a 64 MiB active-receipt budget. Before new operation admission, terminal records beyond a small 64-record window are moved into a hash-verified compressed archive with UUID-sharded compact identity indices; unresolved records are never archived. The original complete result remains available by its operation ID, so this is not a 1,024-command lifetime limit. A bounded recent index presents the latest 128 archived summaries. The archive has a separate 1 GiB serialized-data reservation quota (filesystem metadata/allocation overhead is not included); reaching it refuses further admissions and preserves all receipts. Per-profile records are at most 32 KiB; the profile database is at most 2 MiB and each receipt at most 256 KiB. Reaching a cap refuses new mutations and preserves existing data. Receipts are not silently evicted. Native command previews retain at most 8 KiB per stream (reduced further for a smaller configured response budget), with an explicit truncation flag. Saved `environment_execute` commands additionally retain raw stdout and stderr as separate operation-owned binary artifacts. The preview is a bounded UTF-8 replacement rendering; it is not the original binary stream. Structured result overhead and JSON escaping are reserved before dispatch; structured responses are never truncated into invalid JSON. The explicit Archive completed results action performs the same non-destructive archival. Export/deletion management after the separate 1 GiB archive quota is reached remains an explicit product gap; the implementation refuses admission rather than silently dropping deduplication evidence. A crash during archive reservation may conservatively overcount reserved disk bytes; data remains retained.

## Retained command output

Before command dispatch, the helper reserves up to 16 MiB per stream, 32 MiB of raw bytes per operation, plus bounded metadata against a separate 1 GiB output-storage budget. A bounded private ledger (2 MiB), immutable operation identity and synced original intent survive setup interruption. Per-stream queues hold at most four 16 KiB chunks; fixed-size readers continue draining and counting after a stream reaches its retention cap. The native writer records partial writes and flush failures. Hitting the byte cap does not turn an otherwise confirmed command exit into an unknown effect: capture completeness and command outcome are separate fields. New requests are refused when the quota is exhausted; old results are not silently deleted. This quota covers serialized bytes and reservations, not filesystem block/allocation overhead. Explicit deletion/retention management remains a product gap.

Raw files are published without replacing existing files at `artifacts/environments/<operation_id>/stdout.bin` and `stderr.bin`. An adjacent `manifest.json` binds the operation ID, environment ID, original request digest, SHA-256 and stored size of each stream. It contains no argv, credentials or saved profile. The private capture area retains recovery metadata under `native-management/environments/captures/<operation_id>`. Successful terminal ordinary receipts retain full artifact references through receipt archival; bounded history summaries omit the stream contents. A command label contains only a bounded program basename, never its arguments. The recorded creation time orders saved command history; old receipts may have no timestamp or label.

Each `EnvironmentOutput.artifacts` entry contains `stream`, `path`, `sha256`, `stored_bytes`, `observed_bytes`, `observed_bytes_exact`, `complete` and `reason`. `complete:true` means the retained client stream reached EOF with no retention/read/write interruption. It does not verify remote side effects. Reasons include `eof`, `cancelled`, `timed_out`, `byte_limit`, `read_error`, `write_error` and `interrupted`. `observed_bytes_exact:false` marks a lower bound after an interrupted reader or recovered prefix; it must not be presented as an exact discarded-byte count. Empty legacy artifact lists mean there was no raw capture, rather than an empty complete stream.

Cancellation, timeout and dropped callers stop the local process tree and preserve the actual retained prefix. Local client termination still cannot prove remote completion. The ordinary caller waits a bounded cleanup interval; if native disk I/O is still finishing, it returns an unknown receipt and directs the user to Check result. Actual readers, blocking writers, finalizers and their storage/resource/operation/profile leases remain alive until the work actually ends. Helper idle eviction counts these jobs. A process restart reconciles the same operation; it never repeats the command. Interrupted setup at any boundary between reservation and per-operation intent remains discoverable through the bounded ledger. Missing metadata alone does not prove non-dispatch: reconciliation reports unknown, retains existing prefixes, and releases only unused byte reservations after quiescent finalization. Metadata or interrupted reservation overcounts remain conservative until reconciliation.

All output paths are generated by the application. Unix uses held directory descriptors with no-follow relative traversal and refuses symlinks, special files and unknown hard links. Atomic no-clobber publication uses a link/unlink pair; recovery accepts only the exact two known aliases with matching inode and digest, and refuses third or unrelated aliases. Newly created directory entries and staged/published files are synced before acknowledgement. Windows uses held local-volume directory handles and relative `NtCreateFile`/rename operations, refuses reparse/device/UNC/ADS/hard-link aliases, and uses dedicated writable handles for flushing private staging. Artifact verification remains read-only. Directory authorities and leases coordinate app-owned processes; this is not a sandbox against a malicious process already able to mutate this account's private storage between syscalls. File hashes detect later content changes. Power-loss behavior and native Windows execution require OS-specific qualification; Windows directory flush is not asserted.

## Application and agent API

The direct helper management API returns JSON values:

| Name | Arguments | Result |
| --- | --- | --- |
| `helper_environment_clients` | `{}` | Installed executable paths, without executing them |
| `helper_environment_list` | `{}` | `environments`, unresolved `operations` summaries, `clients` |
| `helper_environment_save` | `operation_id`, `expected_revision` (0 for new), `profile` | Receipt with the resulting profile revision |
| `helper_environment_status` | `environment_id` | Live status plus saved profile |
| `helper_environment_connect`, `disconnect`, `create`, `start`, `stop`, `remove_container`, `remove` | `environment_id`, `operation_id`, `expected_revision` | Durable receipt; `remove` removes only the profile |
| `helper_environment_operations` | `environment_id` | Bounded receipt summaries including original identities |
| `helper_environment_operation` | `operation_id`, optional original `environment_id` and `action` together | Original receipt, with observation-only recovery if quiescent |
| `helper_environment_maintenance` | `{}` | Archive completed results and report active/archive storage counts |
| `helper_environment_resolve` | `operation_id`, `succeeded`, nonempty inspection `note` | Explicitly reconciled receipt; executes no command |

The non-agent `recover_execution(config, args, cancel)` hook lets the application resolve an outer action-journal entry after explicit native-result reconciliation. It reads only an existing catalogue and exact original request digest/environment/action/revision. Terminal success returns the saved completed observation; known failure or cancellation returns the saved failed observation. Missing, pending and unknown outcomes return no result. It launches no command or liveness probe, creates no cancellation fence, and does not initialize unused feature storage.

Only `environment_list`, `environment_status` and `environment_execute` are agent tools. Execute requires `environment_id`, `expected_revision`, `operation_id`, `command` argv and optional bounded `timeout_seconds`. It is always declared as a write and remains subject to the application tool permission policy. Lifecycle/profile helpers are not discoverable agent tools. Raw executable or target overrides in a command request are rejected.

## Qualification and remaining scope

Focused tests use local fake native executables and temporary files. They exercise real process launch/argv, a surviving foreground SSH process, private shared-control paths, ownership checks, profile revisions, receipt reuse, cancellation and restart recovery. They never connect to an SSH account or a real Docker/Podman service. Such fixtures do not establish live server/client-version or cross-platform compatibility.

This backend provides noninteractive command execution and the documented profile/container lifecycle. Native PTY terminals, interactive SSH authentication, persistent shell state, remote file browsing/transfer, image building/pulling and container file/mount management are not implemented by these modules. The deprecated `remote_execute` compatibility executor is absent from normal tool discovery and has no new UI route. Its original arguments are not rewritten into a saved profile. It remains available only to compatibility resolution for exact prior engine checkpoints; completed outer-journal cached results remain unchanged. Its old generic runner retains bounded previews only, with no raw-output capture or qualified native-effect recovery. The supported product path is saved `environment_execute`. These gaps remain part of the wider product goal; the backend does not claim a complete remote IDE or terminal.

Focused validation commands (repository-pinned toolchain; local fake clients only):

```sh
CARGO_INCREMENTAL=0 cargo test --locked --offline -p workbench-capabilities environments:: --lib
CARGO_INCREMENTAL=0 cargo test --locked --offline -p workbench-engine environment_recovery_tests --lib
CARGO_INCREMENTAL=0 cargo clippy --locked --offline -p workbench-capabilities --all-targets -- -D warnings
CARGO_TARGET_DIR="$PWD/target" CARGO_INCREMENTAL=0 cargo check --locked --offline --manifest-path crates/capabilities/validation/windows-read/Cargo.toml --target x86_64-pc-windows-msvc --tests
```

The Windows check compiles the actual output-authority module and its five native test bodies; it does not execute them on macOS. Production-reader tests in the same harness remain distinct from output-storage tests. No live SSH account, Docker/Podman daemon, remote command side effects or cross-platform release acceptance is inferred from these local tests.
